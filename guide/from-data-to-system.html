      2. Your four questions, answered

      Is SHACL applied to OWL, to RDFS, or to RDF?

      To RDF data. It does not need OWL or RDFS.

      Everything in this stack is written in RDF, as triples:

      • the data (an order, its carrier, its weight);
      • the meaning, in RDFS and OWL (a late order is an order);
      • the rules, in SHACL (every order has exactly one carrier).

      SHACL is a different kind of tool from OWL. OWL adds facts that follow from the data. SHACL checks that the data has the right shape. SHACL can use rdfs:subClassOf if it is in the data, which is why our 192 late orders were still checked as orders in Session 4. But a SHACL file works without any ontology.

      Do I need all of them? Are they cumulative or optional?

      No. RDF is the base. The rest are optional, and each adds one thing.

      PieceNeeded?What you get

      Many enterprise knowledge graphs use RDF, a light vocabulary and SHACL, with little or no OWL reasoning. In practice, OWL is the layer teams use least in production. The course teaches it because reuse and reasoning are valuable when you need them, and because you must know what a reasoner can and cannot do.

      Where does the graph live? Do I also need Neo4j?

      The data graph lives in a graph database. Neo4j is an alternative, not an extra layer.

      • Triple store (for RDF): Apache Jena Fuseki in our labs. Examples in industry: Ontotext GraphDB, Stardog, Amazon Neptune, OpenLink Virtuoso.
      • Virtual graph: nothing is stored. A tool such as Ontop answers each SPARQL question by writing SQL on the live database.
      • Property graph database: Neo4j. It stores nodes and relationships with properties, and it uses its own query language, Cypher.

      A knowledge graph is not one product. It is the data graph, plus its ontology, plus its shapes, working together. If you choose Neo4j you normally do not use RDF, OWL or SHACL. Section 3 shows the two routes side by side.

      Where does the ontology live? In Protégé? In a database?

      In a file in git. Protégé is only the editor.

      1. Edit the ontology in Protégé (or a text editor). It is a .ttl or .owl text file.
      2. Commit it to git. The file in git is the source of truth, with a history and reviewers.
      3. Check it automatically in CI: a reasoner (for example ROBOT with ELK or HermiT) and SHACL.
      4. Release it with a version IRI, for example .../scm/1.0.0.
      5. Load the release into the triple store, usually as its own named graph, and publish it at a URL.

      Some commercial products keep the ontology on their own server instead (TopBraid EDG and PoolParty are examples). The git workflow is the open, common one, and it is what this course uses.

      5. What a real release looks like

      1. A person edits the ontology or a shapes file and opens a pull request.
      2. CI runs the reasoner and the SHACL gate on a small sample. A Violation turns the run red and the change cannot be merged.
      3. After the merge, a build job runs the mapping and rebuilds the graph from the live database.
      4. The new graph, ontology and shapes are loaded into the triple store, and the SHACL gate validates the full graph.
      5. The access layer and any dashboards read from the SPARQL endpoint. The test set is run again and the score is recorded with the model name and date.

      Our labs run each of these steps by hand so you can see them. In a company, CI and a scheduler run them for you. kr-team-template is a small working version of the whole flow.
