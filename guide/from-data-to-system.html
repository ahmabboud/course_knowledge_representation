    Question 1 of 8

    How are things connected across our systems?

    The order is in one table, the plant in another, the carrier in a third. To follow a link you must join them, and every new question needs a new join.

    Required Facts that name the same thing the same way.

    Concept: RDF, a graph of facts

    OrderPlantPortCarrier
    1447296446.7PLANT16PORT09V44_3

    The links are hidden inside columns. To use them, you join tables.

    Each link is a fact: order carriedBy V44_3. Each thing has one global name, so facts from any system meet at the same node.

    You can skip it if one clean table answers all your questions. Then a database is enough.

    Where it lives: a triple store, a database for RDF facts. Session 2.

    Tools. In our labs: Apache Jena Fuseki. In industry (examples): Ontotext GraphDB, Stardog, Amazon Neptune, OpenLink Virtuoso.

    Another route. A property graph database such as Neo4j stores nodes with properties and uses its own query language, Cypher. You choose one route per project. The last question helps you decide.

    Question 2 of 8

    What do our words mean? Is a late order an order?

    In the data, 192 orders are marked as class “late order” and the rest as class “order”. Ask how many orders there are, and the answer depends on whether the system knows a late order is an order. RDFS can say it in one line.

    Required, light Class names and a hierarchy: RDFS (RDF Schema). Optional Richer meaning and reasoning: OWL (Web Ontology Language).

    Concept: a vocabulary says what the words mean

    9,023

    “How many orders?” counts only things marked Order. The 192 late orders are missed.

    ul:LateOrder  a rdfs:Class .   # a separate type

    You can skip OWL if you only need class names. Many production systems use RDFS and SHACL, and little or no OWL reasoning.

    Where it lives: a .ttl file in git, loaded into the store. Protégé is only the editor. Session 3.

    Tools. In our labs: Protégé (editor), ELK and HermiT (reasoners). In industry (examples): WebProtégé, TopBraid, PoolParty; reasoning is built into GraphDB and Stardog.

    Question 3 of 8

    How do we know the data is right?

    An order has lost its carrier. Two different tools can read the same RDF data graph and answer differently. Each also reads its own extra rules: the reasoner reads the ontology, and the validator reads the shapes.

    Optional, very common Rules the data must obey (SHACL). It needs no OWL.

    Concept: a shape is a rule a computer checks

    uls:OrderShape a sh:NodeShape ;
  sh:targetClass ul:Order ;          # check every order
  sh:property [ sh:path ul:carriedBy ;
                sh:minCount 1 ;      # at least one carrier
                sh:maxCount 1 ] .    # at most one

    You can skip it if the data never changes and someone checks it by hand. For a live system, keep it.

    Where it lives: a .ttl file in git, run by pySHACL in CI and before data is loaded. Session 4.

    Tools. In our labs: pySHACL, shacl-play. In industry (examples): TopBraid SHACL; validation built into GraphDB and Stardog.

    Question 4 of 8

    Where did this fact come from?

    The rule found two orders that weigh 0 kg. To fix them we must know which file, which run, and which version of the rules.

    Optional, but you will want it A record of source, process and release (provenance, version IRI).

    Concept: provenance is the record of where data came from

      You can skip it if you can always rebuild everything from one source in seconds, and nobody audits the result.

      Where it lives: written when the graph is built, stored as its own graph; the ontology release is a version number in its file. Session 4.

      Tools. In our labs: PROV-O triples written by a script, and a version IRI in the ontology file. In industry (examples): the same W3C standard, PROV-O.

      Question 5 of 8

      The data lives in a database that changes every day.

      A script that converted four files once is not enough. A mapping describes how rows become facts, so any tool can rebuild the graph when the data changes.

      Required if your data is in a database A mapping, written in R2RML (the W3C mapping language), and a choice: store the graph, or ask the database live.

      Concept: materialize or virtualize

      Materialize

      Convert once, store the graph.

      9,215

      orders in the stored graph

      Virtualize

      Ask the live database each time.

      9,215

      orders, asked just now

      Illustration: one extra order is added so you can see the difference.

      You can skip it if your data is a few files that rarely change. A conversion script is fine.

      Where it lives: the mapping is a file in git. Session 5.

      Tools. In our labs: Morph-KGC (materializes), Ontop (virtualizes). In industry (examples): Ontop, other RML tools, commercial integration tools.

      Question 6 of 8

      Can people ask in plain language?

      Managers do not write SPARQL, the query language for graphs. A language model (an AI that writes text and code) writes the query, the system checks it against the graph's description, and it refuses what the graph cannot answer.

      Optional An access layer: schema, examples, a check, a refusal path.

      Concept: the access layer

      You can skip it if your users are analysts who write queries themselves.

      Where it lives: code and a test set in git, run as a service in front of the SPARQL endpoint. Session 7.

      Tools. In our labs: our access layer with Gemini. In industry (examples): features in graph platforms, or a language model plus SPARQL as we built.

      Question 7 of 8

      How do we keep it working when people change things?

      Everything is a file in git, which keeps every version of every file. CI (continuous integration) runs a check automatically on every change. If the check finds a violation, the change is stopped.

      Required in practice Git, CI, and containers that start the whole stack with one command.

      Concept: the gate

      You can skip it if you work alone on a throwaway prototype. Never for a shared system.

      Where it lives: .github/workflows and a Compose file in the repository. Sessions 4, 7 and 8.

      Tools. In our labs: GitHub Actions, Docker Compose. In industry (examples): GitHub Actions, GitLab CI, Jenkins; Kubernetes for larger systems.
