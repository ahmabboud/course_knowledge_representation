Part 1 of 5 · Fundamentals: what the words mean and how they relate · about 50 minutes

Three correct counts of late orders show why a program needs a written definition of “late”.

The disagreement is in the word, not in the data. An ontology is a written list of what such words mean. This part explains what it is, what it is written in, and how it relates to databases, knowledge graphs and reasoners.

Why we need written definitions

Three definitions of “late” give 57.3%, 54.8% and 23.7% of the same 65,752 DataCo orders (Session 1).

Late means: any delay
57.3%

Days it really took (Days real) are more than the days promised (Days scheduled).

Late means: the label says so
54.8%

The dataset's own column Delivery Status says “Late delivery”.

Late means: more than a day
23.7%

Days it really took are more than one day above the days promised.

The problem

Every number is correct: the meaning of “late” lives in people's heads, not in the data. A dashboard, a model and a report can each pick a different one, and nobody notices.

The fix this session builds

Write the meaning down once, precisely, so every program reads it the same way. That is what an ontology is for.

What an ontology contains

An ontology lists the kinds of things, the particular things, and the links between them.

Defined on this slide
Ontology
A written list of the kinds of things in one subject area and the links between them.
Class
A named kind of thing, a box here (a circle later): Shipment. “subclass of” joins two classes.
Individual
One particular thing, a pill: carrier V444_1. “is a” joins it to its class.
Property
A named link, an arrow: handled by.

Real Brunel order and carrier (Sessions 1 and 2). V444_1 is an anonymised code, not a company; flagging it as sanctioned is our teaching choice.

Four words that are easy to confuse

An ontology is written in RDF, using the words of RDFS and OWL

The one sentence to keep: OWL is not an ontology. It is the language you write one in, the way English is not an essay.

“Every sanctioned carrier is a carrier” needs only RDFS. “At risk means a shipment handled by some sanctioned carrier” needs OWL.

The published ontologies we build on

Our ontology imports three published ontologies: BFO, IOF Core and SCRO

Defined on this slide

Upper ontology: a very general list of kinds of things, such as things that last and things that happen. BFO is one.

How the layers relate

BFO is the base layer. It says what kinds of things exist at all.

IOF Core adds industry concepts on top of BFO.

SCRO adds supply chain classes on top of IOF Core, such as Shipment and Carrier.

“On top of” means: our ontology and each layer import (load) the statements of the layer below, so their rules apply to us.

Why reuse them

Someone else's shipment is then the same shipment as ours, and their tools and data work with our file.

Classes drawn as circles

A class is a set: a circle holds its members, and a subclass is a circle inside a circle.

Circle = class · dot = individual · a circle inside a circle = a subclass. Shipments 1447291369.7 and 1447311670.7 sit inside At-risk shipment (a sanctioned carrier handles them); shipment 1447385217.7 does not.

Defined on this slide
Member
An individual inside a class: a dot inside a circle.
Class as a set
A class is exactly the set of its members.
Subclass
A is a subclass of B when every member of A is also a member of B: circle A sits inside circle B.
Classes in a tree

Classes sit in a tree from general to specific: every late shipment is a shipment.

Defined on this slide
owl:Thing
The class of everything. Every class sits somewhere below it. The prefix owl: marks a word that is part of OWL (slide 7).
How to read a line

Each line is a subclass of the line above it: every late shipment is a shipment. It joins two classes, so it is not the “is a” arrow of slide 6, which joins one particular thing to its class.

Why a tree, not a list

If Shipment has a weight, then every late, cancelled and at risk shipment has one too. You write it once.

Properties

A property links a thing to a thing, to a value, or carries a note for people.

Defined on this slide
Object property
Links a thing to a thing: handled by.
Datatype property
Links a thing to a plain value (a number, date or text, called a literal in Session 2): weight in kg. A value cannot start another arrow.
Annotation property
Attaches a note for people, such as a name (rdfs:label) or a comment. No program draws a conclusion from it.
Two parts of an ontology file

An ontology file has two parts: definitions of kinds of things, and facts about particular things.

Defined on this slide
Axiom
One statement in an ontology. Each white box above is one axiom.
TBox
The definitions part: axioms about classes and properties.
ABox
The facts part: axioms about particular things.

Same data as Session 2. The ABox is the same kind of data as the Session 2 graph (orders, carriers, plants). Both parts are RDF triples.

Why keep them apart. Change definitions without touching facts, and load new facts without touching definitions. In Session 5 the facts come from the database; the definitions stay hand written.

Why we need a reasoner

A reasoner checks all 4,819 axioms, including imported ones, in seconds, which no person can do by hand.

Defined on this slide

Reasoner: a program that works out the facts that follow from what you wrote, and tells you when what you wrote contradicts itself.

Inference: a fact the reasoner derived that nobody wrote down.

Imports: our file loads the axioms of other published ontologies, so they count as part of ours (slide 9).

Why by hand does not work

Our own file is small (about 30 classes and properties). Most axioms come from what it imports, and one wrong axiom anywhere can change the meaning of ours.

What a reasoner computes

A reasoner does three computations: consistency, classification and realization.

Consistency

Can all the axioms be true together? Late shipment and Cancelled shipment are disjoint: no shipment is in both. One placed in both: no.

Classification

Work out the full class tree, including links nobody wrote: At-risk shipment is defined as a Shipment handled by at least one Sanctioned carrier, so it is a subclass of Shipment.

Realization

Place each individual in its classes. Shipment 1447291369.7 is handled by sanctioned carrier V444_1, so it belongs to At-risk shipment.

Defined on this slide
Consistent
All the axioms can be true together. Inconsistent: they cannot, the ontology contradicts itself.
Classification
Working out the full class tree.
Realization
Working out which classes each individual belongs to.

You define a class such as “at risk shipment” with six words: some, only, and, or, not, exactly.

At risk here means: a shipment handled by a sanctioned carrier. Protégé shows these six words on every screen.

“handled by some Sanctioned carrier” is the class of shipments with at least one sanctioned carrier.

Defined on this slide

some

The readable way Protégé writes definitions, with the words some, only, and, or, not.
The word only

“handled by only Sanctioned carrier” holds when every carrier a shipment has is sanctioned, even if it has none.

Defined on this slide
only

Englishevery carrier of this shipment, if it has any, is sanctioned

Common mistake

A shipment with no carrier recorded is still in the class: only says no link goes outside the circle, and with no links none does. only never says a link exists. To say both, write some and only.

Combining classes

And, or and not build new classes; disjoint is a different statement saying two classes share no member.

and · intersection

Members of both classes.

Shipment and ('handled by' some 'Sanctioned carrier') is the class At-risk shipment.

or · union

Members of either class.

'Late shipment' or 'Cancelled shipment'

not · complement

Everything outside the class.

Carrier and not 'Sanctioned carrier'

Different: disjoint

Two classes that share no member: it builds no new class. An individual in both is a contradiction.

'Late shipment' DisjointWith 'Cancelled shipment'

Written the way Protégé shows it. Shaded area = the new class. The disjoint axiom is real, from our lab file; BFO adds many more (Part 4).

Counting links

A cardinality restriction counts links, for example exactly one supplier or at least two routes.

In the Brunel data

V444_0 ships on 2 routes, V44_3 on 3, V444_1 on 1. V444_0 and V44_3 count as multi route carriers only if their routes are declared different: OWL does not assume that two names are two different things.

Defined on this slide
Cardinality restriction
A restriction that counts links: exactly 1, min 2 (at least 2), max 3 (at most 3).
Sole sourced component
A component bought from exactly one supplier.
Multi route carrier
A carrier that handles shipments on at least two shipping routes.
Part 3 of 5 · What the reasoner does with what you wrote · about 26 minutes

A reasoner adds the facts that follow from your definitions, and reports when definitions clash.

This part shows it on our ontology: a fact a database refuses and OWL accepts, definitions that place shipments in classes, and a class that cannot have any member.

What OWL does with a fact the database refuses

A database refuses a fact about an unknown shipment. OWL accepts it and concludes the shipment's type.

A reasoner is the program that works out facts that follow from what you wrote. Left: the database. Right: OWL, on the same fact.

CREATE TABLE shipment (id TEXT PRIMARY KEY);
CREATE TABLE carrier (id TEXT PRIMARY KEY);
CREATE TABLE handled_by (
  shipment TEXT REFERENCES shipment(id),
  carrier TEXT REFERENCES carrier(id));
INSERT INTO handled_by
  VALUES ('1447311670.7', 'V444_1');
IntegrityError: FOREIGN KEY constraint failed

Why it fails: the shipment table holds only 1447291369.7. Shipment 1447311670.7 is not in it, so the foreign key refuses the row.

Same as RDFS in Session 2: domain and range add facts, they refuse nothing. Refusing data is a constraint. That is SHACL, Session 4's checking tool.

SubClassOf and EquivalentTo

If “At-risk shipment” is defined with EquivalentTo, the reasoner places matching shipments in it; SubClassOf never does.

SubClassOf · one direction

Every at risk shipment is handled by a sanctioned carrier, but not the reverse: a matching shipment is not placed in the class.

EquivalentTo · both directions

A shipment is at risk exactly when a sanctioned carrier handles it: a matching shipment is placed in the class.

ELK: a fast reasoner that understands only part of OWL (Part 5).

How to read it. Each column is a shipment. “no”: the reasoner did not place it in At-risk shipment. “at risk”: it did. V444_0 is not sanctioned, so shipment 1447385217.7 is correctly never at risk. The lab's first file used SubClassOf only.

Properties with extra declarations

A property can be declared transitive, functional or inverse, and the reasoner derives facts from that.

Transitive

Transitive: if A is part of B and B is part of C, the reasoner derives that A is part of C. (A generic picture, not course data: Brunel has no parts list.)

Functional

Functional: at most one value per thing, one order date per order. If a second, different date arrives, the ontology is inconsistent: the reasoner reports a contradiction.

Inverse

Inverse: the same link read backwards. From “the shipment is handled by V444_1” the reasoner derives “V444_1 handles the shipment”.

Part 4 of 5 · Reusing published ontologies and BFO in detail · about 30 minutes

Reusing an ontology means accepting its axioms, including ones we did not read.

Part 1 showed the stack: BFO, IOF Core, SCRO and our extension (slide 9). Here we look at BFO's categories and at a real mistake that came from reusing a property.

BFO's first split

BFO divides everything into continuants (things that persist) and occurrents (things that happen).

Defined on this slide
Continuant
Something that persists through time: a truck, a warehouse, a purchase order.
Occurrent
Something that happens and unfolds in time: a delivery.

A test. Can you ask “how long did it take?” Then it is an occurrent. Can you ask “where is it now?” Then it is a continuant.

Why it matters. BFO declares many pairs of classes disjoint (nothing can be in both). The next slides show the pair behind our unsatisfiable class.

The truck is an illustration: Brunel records carriers, not their trucks. The order is real.

Three kinds of continuant

BFO has three kinds of continuant: things (a truck), features of one thing (its colour) and copyable information.

Defined on this slide
Independent continuant
A thing that exists on its own: a truck.
Specifically dependent continuant
A feature that exists only in one bearer, the thing that has it: the truck's colour or its role as carrier. Destroy the truck and both are gone.
Generically dependent continuant
Information that can be copied between bearers: the text of a purchase order survives in its copies.

The rule that matters for the lab: BFO says these three kinds share no member, they are disjoint. A physical thing is never a feature of another thing and never a document.

An inconsistent ontology, step by step

Giving a purchase order a “handled by” link makes the whole ontology inconsistent.

Real run

python local_reasoner.py workspace/domain-mistake.ttl answers: “The ontology is inconsistent: it contradicts itself, so every answer is worthless.”

Two different outcomes

One unsatisfiable class (slides 27 and 34) is empty, and the rest of the ontology still works. An inconsistent ontology, as here, contradicts itself as a whole, so none of its answers can be trusted. The cause is the same kind of mistake: a domain applies to every thing that has the property.

Why a class is unsatisfiable

Protégé explains an unsatisfiable class with a justification: six axioms, one ours and five imported.

1Ours: the class orders some product that depends on some sole sourced component.
2The property depends on product has the domain SupplyRelationship.
3A supply relationship is a specifically dependent continuant.
4Our product is a material product, a kind of material entity.
5A material entity is an independent continuant.
6BFO: independent, specifically dependent and generically dependent continuants are disjoint.

Justification: the smallest set of axioms that together cause a conclusion; remove any one and it goes away. A class can have several; one is enough to fix. Only line 1 is ours, so the mistake is in how it uses SCRO. The next slide decodes lines 2 to 6.

The lab's unsatisfiable class, explained

A reused SCRO property put our product in two disjoint classes, so our class has no member.

Linking to other ontologies

owl:sameAs and owl:equivalentClass merge two things completely, so one wrong link spreads every fact across both.

Example of the harm

Brunel's carrier V444_1 is sanctioned. If another source has a different company also called V444_1 and we link the two with owl:sameAs, that company becomes sanctioned too, and all its shipments are at risk.

Defined on this slide

owl:sameAs: two names for exactly the same individual. The reasoner merges everything said about them.

owl:equivalentClass: two classes with exactly the same members. Every definition of one applies to the other. It is what Protégé calls EquivalentTo (slide 24).

Safer

Prefer rdfs:subClassOf (the “every X is a Y” link) until you can defend the equivalence. “Probably the same” is a similarity claim for Session 5's entity resolution (deciding which records describe the same real thing), with a confidence.

Part 5 of 5 · OWL profiles and the working method · about 22 minutes

OWL has smaller versions called profiles. They reason faster, but you can say less.

This part covers the profiles first, then the method for building an ontology: write the questions, reuse, run both reasoners, fix the model.

OWL profiles

OWL has four profiles: three restricted ones that reason faster, and DL, which allows all of OWL’s words.

ProfileBuilt forCannot sayProgram that reasons
EL · the words some and andVery large class treesonly, counting, notELK, fast
QL · query languageAsking questions of data kept in a relational databasecounting, and several other wordsOntop (Session 5) rewrites a question into SQL
RL · rule languagePrograms that apply if then rulessaying that an unnamed thing existsrule engines
DL · description logic, all of OWLEverything OWL can saynothing, but can be slowHermiT, complete

Each class in our file records its profile in a ul:profile note: the profile is a decision you record, not something you discover later.

Defined on this slide
OWL profile
A part of the OWL language: a list of which words you may use. ELK and HermiT are programs, not profiles.
ELK
A fast reasoner that understands only the EL profile; it ignores other axioms, such as counting.
HermiT
A slower reasoner that understands all of OWL DL, so it reads every axiom.
Decidable
A reasoner is guaranteed to finish with a correct answer. OWL DL is decidable: it always finishes, but may be slow.

So what

Both reasoners find Order for a sole-sourced good (slide 34). Only HermiT also finds Sole-sourced component. A fast reasoner that says “no errors” only means no errors it can see. Run the complete one before you ship.

The working method

Build an ontology in this order: write competency questions, reuse, extend, run both reasoners, fix the model.

Exercise: put the steps in the order you will work in (drag, or use the arrow buttons).

  • Extend SCRO only where a question needs a class it lacks
  • Write the competency questions the organisation actually asks
  • Read the Inferred tree and fix the model, not the output
  • Search for a published ontology that already answers them
  • Run ELK (fast), then HermiT (complete)
Defined on this slide

Competency question: a question the ontology must be able to answer. Example: “Which purchase orders are for a finished good that depends on a sole sourced component?”

Why this order

You cannot judge whether a published ontology covers you until you know what you ask. A class earns its place by answering a question; if you cannot name it, delete the class. Each class in our file records its question in a ul:answersCQ note (eight questions, in competency_questions.md).

Glossary of Session 3: the words you need to read an ontology and a reasoner report.

Ontology
A written list of what the words of one subject area mean, stored as an RDF file.
RDF · RDFS · OWL
The triple format · small word set in it · bigger word set in it. OWL is not an ontology.
Class · individual
A kind of thing · one particular thing.
TBox · ABox
Definitions of kinds · facts about particular things.
some · only
At least one link · every link, if any.
Disjoint
Two classes with no member in common.
Domain · range
Anything with the link is in the domain class · anything it points to is in the range class.
Defined class
A class written with EquivalentTo: anything that meets it is placed in it.
Reasoner
A program that works out the facts that follow from what you wrote.
Classification
The reasoner working out the full class tree.
Unsatisfiable
One class can have no member.
Inconsistent
The whole ontology contradicts itself. (Consistent: no contradiction.)
Justification
The few axioms that together cause a conclusion.
Imports
Loading another ontology's axioms into yours.
BFO · SCRO
Published ontologies we build on: the base layer · supply chain classes.
OWL profile · ELK · HermiT
A part of OWL · a fast reasoner for part of it · a slower reasoner for all of it.
Wrap · the main point

A reasoner takes every axiom as true, so a wrong axiom shows up as an unsatisfiable class.

It follows your axioms exactly, even the wrong ones. That is why it can show you what you did not mean.
