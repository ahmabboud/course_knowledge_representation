What you have

The 9,215 Brunel orders as a graph (Session 2). An ontology that says what the words mean (Session 3). The business rules from Session 1, written as normal sentences.

What is missing

Nothing runs those rules yet. In Session 3 we saw that OWL does not check them: OWL infers new facts, it does not report errors. Today's tool reports errors.

RML RDF Mapping Language: rules that turn CSV, JSON or XML files into RDF. GNN Graph neural network: a model that learns about a node from the nodes next to it, by passing messages along the edges.

Objective

By the end you can turn a business rule into a check, run the check on the real graph, read the report as a list of things to fix, and make every change pass the check before it is accepted.

The untyped shipment of order 1447311670.7 was not refused: OWL concluded it was a Shipment. Inferring is what OWL is for; checking is not.

The same rule, as code

This is the SHACL rule, and this is what the computer answers.

# SHACL: says an order must have exactly one carrier.
uls:OrderShape a sh:NodeShape ;
  sh:targetClass ul:Order ;          # which nodes to check
  sh:property [
    sh:path ul:carriedBy ;           # which property
    sh:minCount 1 ;                  # at least one value
    sh:maxCount 1 ;                  # at most one value
    sh:message "An order has exactly one carrier." ] .
Conforms: False
Results (1):
Constraint: MinCount
Severity:    sh:Violation
Focus Node:  order 1447291369.7
Result Path: ul:carriedBy
Message:     An order has exactly
             one carrier.
Read the shape like a sentence

Check every ul:Order. ul:carriedBy must have at least 1 and at most 1 value. Otherwise: Violation.

The one idea behind this session

OWL: the graph is part of the truth. SHACL: the graph is the whole truth.

Defined on this slide
Open world assumption
If a fact is missing, it is unknown, not false.
Closed world assumption
If a fact is missing, it is false. SQL databases work this way.
Two tools, two jobs

Use OWL to add facts that follow from the data. Use SHACL to check the data you have. A real system uses both on the same graph.

What goes wrong in real data

Four everyday data errors. OWL accepts all four. SHACL reports all four.

A missing value

Order 1447291369.7 with no carrier.

OWL: Some carrier exists, name unknown.

SHACL: MinCount: Violation.

One value too many

An order carried by both V444_0 and V444_1.

OWL: If carried by is functional, OWL decides that the two carriers are the same carrier.

SHACL: MaxCount: Violation.

A value outside the list

Service level "DTX", a typo for DTD.

OWL: A string, like any other.

SHACL: In ( CRF DTD DTP ): Violation.

A value that is too small

Orders 1447336276.7 and 1447215484.7 weigh 0 kg.

OWL: 0 is a valid decimal number, so OWL reports nothing.

SHACL: MinExclusive 0: Violation, on the real data.

Check question

Every order is carried by some carrier. Order 1447291369.7 has none. What does HermiT report?

Part 2 of 5 · about 30 minutes

How do you tell a computer: every order has exactly one carrier?

You describe the shape that the data must have. The computer compares the data with the shape.

How validation works

A shape selects nodes, checks each node, and reports each broken rule

Defined on this slide
Shape
A named set of rules that some nodes of the graph must obey.
Target
Which nodes a shape checks, for example every member of a class.
Also defined here
Focus node
The node being checked when a shape runs.
Validation report
SHACL's output: conforms or not, and one result per broken rule.
Writing a shape

One node shape for “every order”, one property shape per rule

uls:OrderShape a sh:NodeShape ;
  sh:targetClass ul:Order ;
  sh:property [ sh:path ul:carriedBy ;
    sh:minCount 1 ; sh:maxCount 1 ; sh:class ul:Carrier ] ;
  sh:property [ sh:path ul:serviceLevel ;
    sh:in ( "CRF" "DTD" "DTP" ) ] ;
  sh:property [ sh:path ul:weight ;
    sh:datatype xsd:decimal ; sh:minExclusive 0 ] .
# four more property shapes in the file
Defined on this slide
Node shape
A shape about a whole node: every order.
Property shape
A shape about one property of that node: exactly one carrier.
Which version

We use SHACL 1.0, an official W3C standard since 2017. SHACL 1.2 is still a draft (3 August 2026), so we build on 1.0.

The most common SHACL bug

A shape that selects no nodes checks nothing, but the report still says “conforms”

$ python validate.py \
    --shapes shapes_template.ttl
focus nodes 0  PurchaseOrderShape
               <- targets nothing
validated in 0.6 s.
conforms (SHACL): True
GATE: PASS, no violations.

The template targets ul:PurchaseOrder. Our graph has 9,215 ul:Order nodes and not one ul:PurchaseOrder.

A passing result is not proof

If there are zero focus nodes, nothing was checked. Read the number of focus nodes before you read the result.

Our tools show it first

validate.py prints the focus nodes of every shape before it validates. shacl-play warns “Shapes did not match anything!”

Why nobody saw them

A profile shows the minimum weight (0) among dozens of other numbers, so it is easy to miss. A rule that says above 0 cannot be missed.

Is the rule wrong, or is the data wrong?

Hundreds of units cannot weigh nothing. The rule is right and the two rows are wrong. Part 3 gives this decision a name: triage.

Defined on this slide
Severity
How serious a broken rule is: Violation, Warning or Info, set per rule with sh:severity.
The rule in SHACL 1.0

sh:conforms is true only when there are no results of any severity. Our triaged run: conforms false.

The rule in our gate

validate.py fails only on a Violation. Warnings are printed and pass. pySHACL's own switch for this is allow_warnings.

When core SHACL cannot say it

The rule compares the order's port with its plant's ports. That needs a query.

uls:LinkedPortShape a sh:NodeShape ;
  sh:targetClass ul:Order ;
  sh:sparql [
    sh:message "{?port} is not a port of {?plant}." ;
    sh:prefixes <https://ul.edu.lb/kr/shapes> ;
    sh:select """
      SELECT $this ?plant ?port WHERE {
        $this ul:fromPlant ?plant ;
              ul:shipsFrom ?port .
        FILTER NOT EXISTS {
          ?plant ul:servesPort ?port }
      }""" ] .
Defined on this slide
SHACL-SPARQL
A SHACL rule written as a SPARQL query. Each row the query returns is one result.
$this
The focus node being checked, filled in for every order in turn.
Result on Brunel

0 of 9,215 orders break it. The Session 1 rule holds for every order, and now a computer has checked it.

Defined on this slide
Triage
Going through a report result by result, and deciding for each whether the rule or the data is wrong, and what to do.
Three possible decisions

The rule is wrong: change the rule. The data is wrong: fix the source and keep the rule. We know about it and accept it for now: lower the severity, and write until when.

Provenance, drawn

Three kinds of thing answer: where did it come from, how was it made, and who did it?

Defined on this slide
Provenance
The record of where data came from, who produced it, and how.
Also defined here
PROV-O
The W3C ontology for writing provenance as triples: entities, activities, agents.
Provenance is queryable

One SPARQL query goes from a triple to its file, its run and its time

SELECT ?g ?file ?run ?time WHERE {
  GRAPH ?g {
    order:1447296446.7 ul:carriedBy ?c }
  GRAPH ?p {
    ?g prov:wasDerivedFrom ?f ;
       prov:wasGeneratedBy ?run .
    ?f dcterms:title ?file .
    ?run prov:endedAtTime ?time } }
graph     graph/brunel/OrderList

finished  2026-09-25T01:31:12+00:00
Why it matters today

If triage says “the data is wrong”, this query shows which file to fix. Later it proves which run fixed it.

Releasing an ontology

The ontology IRI names the ontology. A version IRI names one release of it.

<https://ul.edu.lb/kr/scm#> a owl:Ontology ;
  owl:versionIRI <https://ul.edu.lb/kr/scm/1.0.0> ; # new
  owl:versionInfo "1.0.0" ;                       # new
  rdfs:label "UL Knowledge Representation ..." ;
  owl:imports <https://spec.industrialontologies.org/
      ontology/supplychain/SupplyChain/> .
Defined on this slide
Version IRI
The name of one release of an ontology (owl:versionIRI), next to the ontology IRI that names all its releases.
Why shapes need it

Shapes are written for one release of the ontology. Import the version IRI that you validated against. Then a later change to the ontology cannot break your checks without you noticing.

Defined on this slide
EPCIS
GS1's standard for recording supply chain events: what was seen, where, when and why.
Licence

What EPCIS does that our first draft did not do

Three good habits from a real standard. Each one needs only one line of Turtle.

1 · Write a rule once, reuse it by name
epcis:ObjectEventShape
  sh:property
    epcis:EventTimeShape ;
epcis:AggregationEventShape
  sh:property
    epcis:EventTimeShape ;

Our order and late order rules could share one carrier rule the same way.

2 · Say what must not be there
epcis:
 ChildEPCsForbiddenShape
  sh:path epcis:childEPCs ;
  sh:maxCount 0 .

sh:maxCount 0 forbids a property. EPCIS uses it to keep fields out of event types where they make no sense.

3 · A message a person can act on
sh:message
 "childEPCs should not
  appear within
  ObjectEvent,
  TransactionEvent or
  TransformationEvent"

A person reads the report and fixes the data. Put the fix in the message.
