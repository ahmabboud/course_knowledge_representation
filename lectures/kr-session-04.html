Part one of six · ~20 minutes

A reasoner told you your ontology was fine. Why isn't that enough?

Because "fine" and "true of your data" are different claims, and OWL only ever makes the first one.

Same data, a different question

Nothing was inconsistent. Something was still wrong.

Session 3 ended on this exact assertion, satisfiable under every reasoner in the room:

ul:po88 a ul:PurchaseOrder ;
  ul:hasCarrier ul:carrier-dhl .

ELK and HermiT both accept it. Neither one asks whether ul:carrier-dhl is actually a declared ul:Carrier, or whether this order has a carrier at all.

The question OWL answers

Could a model of the world exist in which this is true? For almost any assertion, yes, a reasoner can always imagine an unseen individual that makes it work.

The question you actually have

Is it true of this data, right now, with nothing left to imagine? That is a different question, and it needs a different tool.

Definition

The open world assumption, stated exactly

OWL, RDF and every reasoner you used last week are built on it.

  • ul:po88 has no asserted ul:deliveryDate. OWL does not conclude it has none, it concludes only that none is known.
  • This is correct for schema-level modelling: a published ontology can never enumerate every individual that will ever be asserted against it.
  • It is wrong for one specific job: telling you your dataset is complete and clean.
Say it back

"No delivery date on file" and "this order was never delivered" are different claims. OWA only ever lets you make the first one.

Definition

The closed world assumption, stated exactly

is how SQL, forms, and every quality report you have ever trusted already work.

  • A validator working under CWA can say "this order has no carrier" and mean it.
  • SHACL validates a fixed data graph, not an open-ended set of possible models.
  • This is why SHACL, not OWL, is the tool for a quality report.
One graph, two disciplines

The same triples. OWL asks "is this satisfiable, in general?" SHACL asks "does this specific graph satisfy this specific shape, right now?"

The same axiom set, two answers

Drag the seam. Same triples, different discipline, different verdict.

ul:po88 a ul:PurchaseOrder .
(no ul:hasCarrier asserted)

"Satisfiable. A carrier may
exist that was not stated."
consistent, classifies fine
ul:po88 a ul:PurchaseOrder .
(no ul:hasCarrier asserted)

"Violation. ul:hasCarrier
sh:minCount 1 is not met."
sh:conforms false
Keep OWL for
  • Schema-level meaning, reuse, classification.
  • Questions about what is possible in any model.
Bring in SHACL for
  • Is this graph, as it stands, complete and well formed?
  • A report a data owner can act on, pass or fail.
A concrete catalogue

Four failures your Session 3 ontology cannot see

01 · Missing data

Missing carrier

OWA reads this as unknown, not absent. A real order with no carrier is a data-entry gap.

02 · Cardinality

Three carriers

OWL allows it unless you declared a max cardinality axiom, which most teams skip, for reuse.

03 · Cross-field

Backwards dates

A relationship between two datatype values. No OWL construct compares two literals directly.

04 · Untyped ref

An untyped IRI

ul:hasCarrier ul:untracked: ul:untracked is never asserted a ul:Carrier.

Two of these four fail for real, this session, on data extending ul:po88. The other two are your lab work.

Architecture

A validator, not a second ontology

  • Ontology (OWL)What the terms mean. Session 3's job, unchanged today.
  • Data graphYour team's own instance data, mapped or asserted.
  • Shapes graph (SHACL)A separate RDF graph of constraints, targeted at the same data.
  • Validation reportRDF, machine-readable, checked into your repository.
Worth saying plainly

SHACL shapes are themselves RDF triples, written in Turtle, living in their own file. Nothing new to install, nothing new to learn about the graph.

Part two of six · ~28 minutes

A shape is a claim about a node. What can that claim actually say?

Eight component families cover almost everything your constraint inventory needs.

Anatomy

Two shape kinds, nested inside each other

  • A constrains a node directly: which class of individual, and what must hold of it.
  • A constrains what you reach by following one property.
  • A NodeShape lists PropertyShapes with sh:property. Most real shapes are a NodeShape wrapping several PropertyShapes.
ul:PurchaseOrderShape
  a sh:NodeShape ;
  sh:targetClass ul:PurchaseOrder ;
  sh:property [
    sh:path ul:hasCarrier ;
    sh:minCount 1 ;
  ] .

The square brackets are a blank node PropertyShape, anonymous and inline. Give one its own IRI only if you reuse it elsewhere.

Targeting

Four ways to say which nodes a shape checks

sh:targetClass
Every instance of a class. The one you will use almost everywhere: sh:targetClass ul:PurchaseOrder.
sh:targetNode
One named individual, by IRI. Rare in a shape graph, common while debugging one bad record.
sh:targetSubjectsOf
Every node that is a subject of a given property, whatever its class. Useful when a property crosses several classes.
sh:targetObjectsOf
Every node that is an object of a given property. Targets the value end of a relation, not the source end.
The trap

No target at all means the shape checks nothing, silently. Unlike a missing WHERE clause, SHACL does not error, it just validates zero nodes and reports conformance.

Constraint family 1

How many values are allowed, exactly

sh:path ul:hasCarrier ;
sh:minCount 1 ;
sh:maxCount 1 ;
  • sh:minCount 1 is how SHACL spells "required". There is no separate sh:required.
  • Omitting sh:maxCount means unbounded, not zero. State it if the field is single valued.
  • Counted per sh:path, per focus node, not across the whole graph.
Straight from GS1's own reference shapes

epcis:SchemaVersionShape pairs sh:minCount 1 with sh:maxCount 1 on every mandatory, single-valued field in the real EPCIS document shape. The same pattern, in production, since before this course existed.

Constraint family 2

What kind of value is allowed

sh:datatype
The value is a literal of exactly this XSD datatype: sh:datatype xsd:date.
sh:class
The value is a resource that is an instance of this class, checked against your Session 3 ontology's own rdf:type assertions.
sh:nodeKind
Structural, not semantic: sh:IRI, sh:BlankNode, or sh:Literal. Catches a string where an IRI belonged.
sh:path ul:hasCarrier ;
sh:class ul:Carrier ;
sh:message "hasCarrier must point to a declared ul:Carrier." ;
Constraint family 3 · real examples, not invented ones

Shape the value itself, not just its type

Two patterns lifted directly from GS1's real EPCIS-SHACL.ttl, the file you reuse later this session.

# epcis:EventTimeZoneOffsetShape
sh:pattern "^(\\+|-)((0[0-9]|1[0-3])"
  ":([0-5][0-9])|14:00)$" ;
# epcis:ActionShape
sh:in ( "ADD" "OBSERVE" "DELETE" ) ;
sh:pattern

A regular expression the lexical value must match. Format rules OWL's datatype system cannot express: a national ID, a currency code, an ISO offset.

sh:in

A closed enumeration. GS1 restricts action to exactly three strings, not "any string", the same way a database CHECK constraint would.

Constraint family 4

Combining shapes: or, and, not

  • sh:or, at least one listed shape must hold. GS1's SenderShape allows an IRI or a plain string.
  • sh:and, every listed shape must hold. Common when composing two reusable shapes.
  • sh:not, the shape must fail. GS1 uses it to reject NaN in a numeric field.
sh:or (
  [ sh:nodeKind sh:IRI ; ]
  [ sh:datatype xsd:string ; ]
) ;
Why this matters for your own inventory

Real operational data is rarely one clean type. sh:or is how you validate "a carrier code, or an IRI, either is fine" without loosening the constraint to "anything".

Check question

A shape has sh:severity sh:Warning. The data violates it. What happens to sh:conforms on the report?

Part three of six · ~22 minutes

One core component compares a value against a fixed rule. What compares two values to each other?

Nothing in the core vocabulary. That gap has one answer.

The gap

Delivered before it was dispatched

Every core component you have seen constrains one property against a fixed rule: a datatype, a count, a pattern. None of them compares two properties of the same node to each other.

  • ul:dispatchDate must precede ul:deliveryDate, on the same ul:PurchaseOrder.
  • This is exactly the shape of Session 1's own template example: "a shipment cannot be delivered before it is dispatched."
What you need

A general query over the focus node's own neighbourhood. SHACL has exactly one component that gives you that: sh:sparql.

SPARQL-based constraints

A SELECT that returns the violations

sh:sparql [
  a sh:SPARQLConstraint ;
  sh:message "deliveryDate before dispatchDate." ;
  sh:prefixes ul: ;
  sh:select "SELECT $this WHERE { $this ul:dispatchDate ?d ; ul:deliveryDate ?r . FILTER (?r < ?d) }" ;
] .
  • $this, bound to the focus node once per candidate.
  • Every returned row is one violation. Zero rows, shape satisfied.
  • sh:prefixes reuses prefixes already in your shapes graph.
When to reach for this

Only when a core component cannot say it. More expensive to evaluate, and a bad query can silently match nothing at all.

Diagnostic walkthrough

One shape, built up in four steps, each one adding a constraint family

ul:PurchaseOrderShape a sh:NodeShape ;
  sh:targetClass ul:PurchaseOrder ;
  sh:property [ sh:path ul:hasCarrier ; sh:minCount 1 ; sh:maxCount 1 ] .
  sh:property [
    sh:path ul:hasCarrier ; sh:class ul:Carrier ;
    sh:minCount 1 ; sh:maxCount 1 ;
    sh:message "hasCarrier must be a declared ul:Carrier." ] .
  sh:property [ sh:path ul:dispatchDate ; sh:datatype xsd:date ;
    sh:minCount 1 ; sh:maxCount 1 ] ;
  sh:property [ sh:path ul:deliveryDate ; sh:datatype xsd:date ;
    sh:maxCount 1 ] .
  sh:sparql [ a sh:SPARQLConstraint ;
    sh:message "deliveryDate before dispatchDate." ;
    sh:select "SELECT $this WHERE { $this ul:dispatchDate ?d ; ul:deliveryDate ?r . FILTER (?r < ?d) }" ] .
The output

A report is a graph too, and you read it the same way

sh:conforms
The single boolean bottom line: did every shape hold, across the whole graph.
sh:result
One per violation. A conforming graph has zero.
sh:focusNode
Which node failed. The IRI you go fix.
sh:resultPath
Which property the failure was found on.
sh:resultMessage
Your own sh:message, or a generic default if you did not write one.
Why sh:message is not optional in your work

A report with a generic "does not conform" message is unreadable by anyone but its author. Every shape you write this session gets one.

The decision every violation forces

A failing shape is not automatically a data bug

  1. Read the focus node and the message. Go look at the source row.
  2. Ask: is this genuinely wrong data, or a rule that is too strict for a real, valid case?
  3. If the data is wrong: record it, do not silently fix and re-run. The finding is part of your deliverable.
  4. If the shape is wrong: loosen it deliberately, note why, keep the old version in git history.
This is the actual Milestone 1 grading criterion

"A validation report with every failure triaged" means exactly this decision, written down, for every single violation. Zero violations with no triage log scores worse than a handful, explained.

Part four of six · ~13 minutes

A clean report, dated when, produced by what, against which version?

"Provenance" is in this session's title for a reason: an unattributed quality claim is not a quality claim.

The third word in the session title

A validation report is a claim. Claims need an author and a date.

"The graph conforms" is worthless on its own six months from now: conforms, checked by what shapes, against what data snapshot, run by whom, when?

  • The ontology can change (Session 3's file gets a new class).
  • The shapes can change (you loosen a rule after triage).
  • The data can change (a new export lands next week).
Without provenance

A report that conformed in March, read in September, with no dates or versions attached, tells you nothing about whether it still applies.

Mechanics

Annotate the report, not just the shapes

ul:triage-po99-carrier a ul:TriageDecision ;
  dcterms:created "2026-09-22"^^xsd:date ;
  dcterms:creator "team-4" ;
  prov:wasGeneratedBy ul:validationRun-2026-09-22 ;
  ul:decision "data dirty: carrier code unregistered" .
  • dcterms:created / dcterms:creator cover most of a milestone report, reusing vocabulary already in GS1's own shapes file.
  • prov:wasGeneratedBy (W3C PROV) links a decision to the run that produced it, not just a date.
  • Deliberately lightweight: cite the pattern, do not build the whole PROV-O vocabulary.
Mechanics

owl:versionIRI: which ontology, exactly

<https://ul.edu.lb/kr/scm> a owl:Ontology ;
  owl:versionIRI
    <https://ul.edu.lb/kr/scm/2026-09-22> ;
  owl:versionInfo "0.3.0, post Milestone 1" .
Why it earns its place here, not in Session 3

A validation report is only meaningful pinned to one exact ontology version. Without owl:versionIRI, "clean against the ontology" cannot say which ontology.

What to actually take from it

Not the shapes themselves, the discipline behind them

01 · sh:message, always

Every shape explains its own failure

No shape in the file lacks one. Your inventory shapes get the same rule, no exceptions.

02 · sh:or for real-world messiness

Model the actual variation, not the ideal case

SenderShape accepts IRI or string because real senders arrive both ways. Do not force a false choice.

03 · Nested sh:node for structure

Compose shapes the way you composed ontology classes

EPCISDocumentShape nests EpcisHeaderShape and EpcisBodyShape rather than flattening everything into one shape.

Tooling

A second validator, to sanity-check the first

shacl-play, a free browser tool: paste a shapes graph and a data graph, validate, and generate human-readable shape documentation and a UML-style diagram.

  • Useful for a quick check against a second implementation, pySHACL and shacl-play occasionally disagree at the edges of the spec.
  • The documentation generator turns your shapes graph into a page a non-technical reviewer can read, worth attaching to your milestone submission.
Not a replacement for pySHACL

Your CI gate runs pySHACL, not a browser tool. Use shacl-play for exploration and documentation, not as the system of record.

Part six of six · ~16 minutes

You ran the validator once. What stops the next commit from breaking it again?

Nothing, unless the check runs automatically, every time.

The problem with a report you ran once

A clean report today says nothing about tomorrow's commit

  • A teammate edits the mapping script next week, a new set of dirty rows lands unnoticed.
  • Someone loosens a shape to make a report look cleaner, without a triage note.
  • Both are silent unless something runs the check again, automatically, on every change.
The software engineering answer

The same problem, the same fix, as a broken unit test: run it in continuous integration, and block the merge if it fails.

The provided workflow, read line by line

Four steps, the same commands you ran by hand

on: [push, pull_request]
jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install pyshacl
      - run: python validate.py --fail-on-violation

Checkout the repository, install Python and pySHACL, run the same validate.py from the lab. Nothing here is new, only automatic.

Live, or the closest thing to it

A red check on a pull request is the point, not a failure

Screenshot: a GitHub pull request with the validate check failing, red X visible Capture from this course's own team-template repository once a team has a real failing run. Save as assets/img/s4-ci-red.png, size 1600×900, crop to the checks panel.
Read the red check correctly

It means the gate is doing its job. A gate that never turns red has either perfect data forever, or is not actually wired up. Check which, the second is far more common.

Exactly the same lesson as ROBOT's own non-zero exit on a real violation: a failing check on bad input is correct behaviour, not a bug in the tool.

Independent build · 60 minutes · starts now

Shape your own team's inventory, not the shared case

  1. Open your Session 1 constraint inventory for your own team's topic.
  2. Write one SHACL shape per entry, with sh:message on every property shape.
  3. Run python validate.py after every addition, not once at the end.
  4. Triage every violation: shape wrong, or data wrong. Record the decision.
  5. Add owl:versionIRI and provenance on your triage decisions.
  6. Wire up the provided GitHub Action and confirm it runs on your repository.
This is Milestone 1

Submit your repo link before check-in. Grading rewards triage discipline and a working CI gate, not a zero-violation report.
