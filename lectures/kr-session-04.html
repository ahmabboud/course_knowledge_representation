Part 1 of 5 · about 18 minutes

An order has lost its carrier. Does the reasoner complain?

No. And by OWL's own rules, it is right not to.

The same missing fact, two tools

A reasoner fills the gap with an unknown. A validator reports the gap.

Defined on this slide
SHACL
Shapes Constraint Language: the W3C standard for checking that graph data obeys rules, looking only at the data it is given.
Session 3 did this too

The untyped shipment of order 1447311670.7 was not refused: OWL concluded it was a Shipment. Inferring is what OWL is for; checking is not.

The one idea behind this session

OWL treats the graph as part of the truth. SHACL treats it as the whole truth.

Defined on this slide
Open world assumption
If a fact is missing, it is unknown, not false.
Closed world assumption
If a fact is missing, it is false. How SQL databases behave.
Two tools, two jobs

Use OWL to add what follows from the data. Use SHACL to check the data you actually hold. A real system runs both, on the same graph.

What goes wrong in real data

Four everyday data errors. OWL accepts all four. SHACL reports all four.

A missing value

Order 1447291369.7 with no carrier.

OWL: Some carrier exists, name unknown.

SHACL: MinCount: Violation.

One value too many

An order carried by both V444_0 and V444_1.

OWL: If carried by is functional: the two carriers are the same carrier.

SHACL: MaxCount: Violation.

A value outside the list

Service level "DTX", a typo for DTD.

OWL: A string, like any other.

SHACL: In ( CRF DTD DTP ): Violation.

A value outside the range

Orders 1447336276.7 and 1447215484.7 weigh 0 kg.

OWL: 0 is a decimal: nothing to say.

SHACL: MinExclusive 0: Violation, on the real data.

Check question

Every order is carried by some carrier. Order 1447291369.7 has none. What does HermiT report?

Part 2 of 5 · about 30 minutes

How do you tell a machine: every order has exactly one carrier?

You describe the shape the data must have, and let it compare.

How validation works

A shape picks its nodes, checks each one, and writes one line per broken rule

Defined on this slide
Shape
A named set of rules that some nodes of the graph must obey.
Target
Which nodes a shape checks, for example every member of a class.
Also defined here
Focus node
The node being checked when a shape runs.
Validation report
SHACL's output: conforms or not, and one result per broken rule.
Writing a shape

One node shape for “every order”, one property shape per rule

uls:OrderShape a sh:NodeShape ;
  sh:targetClass ul:Order ;
  sh:property [ sh:path ul:carriedBy ;
    sh:minCount 1 ; sh:maxCount 1 ; sh:class ul:Carrier ] ;
  sh:property [ sh:path ul:serviceLevel ;
    sh:in ( "CRF" "DTD" "DTP" ) ] ;
  sh:property [ sh:path ul:weight ;
    sh:datatype xsd:decimal ; sh:minExclusive 0 ] .
# four more property shapes in the file
Defined on this slide
Node shape
A shape about a whole node: every order.
Property shape
A shape about one property of that node: exactly one carrier.
Which SHACL

SHACL 1.0, a W3C Recommendation since 2017. SHACL 1.2 Core is still a Working Draft (3 August 2026): build on 1.0.

The most common SHACL bug

A shape that targets nothing checks nothing, and the report still says “conforms”

$ python validate.py \
    --shapes shapes_template.ttl
focus nodes 0  PurchaseOrderShape
               <- targets nothing
validated in 0.6 s.
conforms (SHACL): True
GATE: PASS, no violations.

The template targets ul:PurchaseOrder. Our graph has 9,215 ul:Order nodes and not one ul:PurchaseOrder.

Green is not proof

A clean report on zero focus nodes means nothing was looked at. Read the focus node count before the result.

Our tools print it first

validate.py lists every shape's focus nodes before validating. shacl-play warns “Shapes did not match anything!”

Why nobody saw them

Rule wrong, or data wrong?

Hundreds of units cannot weigh nothing. The rule is right; the two rows are wrong. Part 3 names this decision: triage.

Defined on this slide
Severity
How serious a broken rule is: Violation, Warning or Info, set per rule with sh:severity.
The rule in SHACL 1.0

sh:conforms is true only when there are no results of any severity. Our triaged run: conforms false.

The rule in our gate

validate.py fails only on a Violation. Warnings are printed and pass. pySHACL's own switch for this is allow_warnings.

When core SHACL cannot say it

The rule compares the order's port with its plant's ports. That needs a query.

uls:LinkedPortShape a sh:NodeShape ;
  sh:targetClass ul:Order ;
  sh:sparql [
    sh:message "{?port} is not a port of {?plant}." ;
    sh:prefixes <https://ul.edu.lb/kr/shapes> ;
    sh:select """
      SELECT $this ?plant ?port WHERE {
        $this ul:fromPlant ?plant ;
              ul:shipsFrom ?port .
        FILTER NOT EXISTS {
          ?plant ul:servesPort ?port }
      }""" ] .
Defined on this slide
SHACL-SPARQL
A SHACL rule written as a SPARQL query. Each row the query returns is one result.
$this
The focus node being checked, filled in for every order in turn.
Result on Brunel

0 of 9,215 orders. Session 1's rule holds on every order, now checked by a machine.

Diagnostic walkthrough

3,435 Violations. Only 2 are the orders' fault.

Every triage decision lives next to its rule, with the evidence

Defined on this slide
Triage
Going through a report result by result, and deciding for each whether the rule or the data is wrong, and what to do.
Three honest answers

Rule wrong: change the rule. Data wrong: fix the source, keep the rule. Known and accepted for now: lower the severity, and say until when.

Why

Provenance, drawn

Three kinds of thing answer “where from, how, and who”

Defined on this slide
Provenance
The record of where data came from, who produced it, and how.
Also defined here
PROV-O
The W3C ontology for writing provenance as triples: entities, activities, agents.
Provenance is queryable

One SPARQL query walks from a triple to its file, its run and its time

SELECT ?g ?file ?run ?time WHERE {
  GRAPH ?g {
    order:1447296446.7 ul:carriedBy ?c }
  GRAPH ?p {
    ?g prov:wasDerivedFrom ?f ;
       prov:wasGeneratedBy ?run .
    ?f dcterms:title ?file .
    ?run prov:endedAtTime ?time } }

Why it matters today

When triage says “data wrong”, this is how you find which file to fix, and prove later which run fixed it.

Release discipline

The ontology IRI names the ontology. A version IRI names one release of it.

<https://ul.edu.lb/kr/scm#> a owl:Ontology ;
  owl:versionIRI <https://ul.edu.lb/kr/scm/1.0.0> ; # new
  owl:versionInfo "1.0.0" ;                       # new
  rdfs:label "UL Knowledge Representation ..." ;
  owl:imports <https://spec.industrialontologies.org/
      ontology/supplychain/SupplyChain/> .
Defined on this slide
Version IRI
The name of one release of an ontology (owl:versionIRI), next to the ontology IRI that names all its releases.
Why shapes need it

Shapes are written against one release. Import the version IRI you validated against, and a later change to the ontology cannot silently break your checks.

Reuse: read before you write

GS1 publishes the shapes for EPCIS 2.0, its standard for supply chain events

The whole file: 1,137 lines · 30 node shapes · 71 property shapes · 0 SPARQL rules · 0 severities set.

epcis:EventTimeShape a sh:PropertyShape ;
  sh:path epcis:eventTime ;
  sh:datatype xsd:dateTimeStamp ;
  sh:minCount 1 ; sh:maxCount 1 ;
  sh:message "In all EPCIS events, eventTime is
    mandatory, single valued and an
    xsd:dateTimeStamp" .
Defined on this slide
EPCIS
GS1's standard for recording supply chain events: what was seen, where, when and why.
Licence

Its LICENSE file is GS1's intellectual property disclaimer, not an open source licence. Borrow the patterns; read GS1's policy before shipping the file.

What EPCIS does that our first draft did not

Three habits from a real standard, each one line of Turtle

1 · Write a rule once, reuse it by name
epcis:ObjectEventShape
  sh:property
    epcis:EventTimeShape ;
epcis:AggregationEventShape
  sh:property
    epcis:EventTimeShape ;

Our order and late order rules could share one carrier rule the same way.

2 · Say what must not be there
epcis:
 ChildEPCsForbiddenShape
  sh:path epcis:childEPCs ;
  sh:maxCount 0 .

sh:maxCount 0 forbids a property: EPCIS keeps fields out of the event types where they make no sense.

3 · A message a person can act on
sh:message
 "childEPCs should not
  appear within
  ObjectEvent,
  TransactionEvent or
  TransformationEvent"

A report is read by whoever fixes the data. Write the fix into the message.
