Part one of six · ~9 minutes

Your ontology describes classes and properties. DataCo's database describes tables and columns. Who says these are the same thing?

Nobody, until you write it down. That declaration is today's whole subject.

Two models of the same reality

A conceptual model and an operational one, and nothing connecting them yet

Your ontology says a ul:PurchaseOrder has a ul:hasCarrier. DataCo's real schema says a row in purchase_orders has a carrier_code column that is a foreign key into carriers.

  • Both are correct descriptions of the same business fact.
  • Neither format understands the other. A table has no notion of a class hierarchy; an ontology has no notion of a foreign key.
The gap

Something has to declare, explicitly, that purchase_orders.carrier_code pointing at carriers.carrier_code means ul:hasCarrier.

Today's answer

A mapping language. Two real, current ones: R2RML, a stable W3C Recommendation, and RML, its actively developed successor.

Honest framing

The graph stops being a snapshot

  • Sessions 2 through 4 all used a graph that was loaded once, then queried, reasoned over, and validated as a fixed thing.
  • A real enterprise database changes constantly. A mapping either has to be re-run (materialize) or the graph has to not really exist at all, and be computed on demand (virtualize).
  • Both are legitimate, real, production architectures. Today you build one of each, over the same data, and compare them honestly.
Why this is not academic

Your capstone's real data is not a CSV you exported once. It is a live source. The architecture decision you make in today's clinic is one your project actually has to live with.

Part two of six · ~24 minutes

Write the correspondence once. Both engines you use today read the same file format.

Triples maps, logical sources, subject and predicate-object maps: four pieces, reused everywhere.

Know what you are actually standing on

One stable Recommendation, one still-moving successor

R2RML

W3C Recommendation, 2012

Relational-to-RDF only. Stable, unlikely to change, what Ontop's native mapping format is built on.

RML

Final Community Group Reports, 2025

A superset of R2RML covering CSV, JSON, XML and more. A Working Group to formalize it has been proposed but is not yet chartered: the syntax you write today is real and current, but not frozen the way R2RML is.

The two required pieces

Where the rows come from, and what triples they become

<#CarrierMap> a rr:TriplesMap ;
  rml:logicalSource [
    rr:tableName "carriers" ;
  ] ;
  rr:subjectMap [ ... ] ;
  rr:predicateObjectMap [ ... ] .
  • A TriplesMap produces zero or more triples, one iteration per row.
  • Its logical source says where the rows come from: a table name, a SQL query, or, in RML, a CSV or JSON file.
  • Everything else in a mapping fills in what happens per row.
Turning one row into triples

A URI template, and one map per column

rr:subjectMap [
  rr:template "https://.../ul#{carrier_code}" ;
  rr:class ul:Carrier
] ;
rr:predicateObjectMap [
  rr:predicate ul:carrierName ;
  rr:objectMap [ rml:reference "carrier_name" ]
] .
  • The subject map builds one URI per row, using a column value inside { }, and can assert an rr:class at the same time.
  • Each predicate-object map is one column, mapped to one property, on that same subject.
  • A row with a NULL in a mapped column simply produces no triple for that property. Nothing errors.
The pattern you will actually use

rr:parentTriplesMap, the mapping-language version of a JOIN

rr:predicateObjectMap [
  rr:predicate ul:hasCarrier ;
  rr:objectMap [
    rr:parentTriplesMap <#CarrierMap> ;
    rr:joinCondition [
      rr:child "carrier_code" ;
      rr:parent "carrier_code" ] ] ] .
  • Instead of a literal, the object comes from another TriplesMap's subject, matched by the join condition.
  • This is exactly how a foreign key becomes an object property, the first of the four mapping patterns Part 4 covers in depth.
  • Materialized for real with Morph-KGC this session, against the same po88 example Session 4 used.
What most teaching material skips

Logical views: a mapping source that is itself a query

Core RML maps directly against a table. The logical views module lets the logical source be an arbitrary SQL query instead, joining or reshaping data before the mapping ever sees it.

Why it matters

A denormalized report table, or a join across three tables the schema never modeled as one relationship, becomes mappable without touching the database schema itself.

Check question

A TriplesMap has a logical source and a subject map with an rr:template, but no rr:class and no predicate-object maps at all. What happens when it runs?

Part three of six · ~22 minutes

Run the mapping once and load the result, or leave the data where it is and rewrite every query?

Both are real architectures. You build one of each, this session, over the same source.

Materialize, or virtualize

Transform and load, or leave in place and rewrite

Materialize

Morph-KGC

Run the mapping, get a real RDF graph, load it into your triple store. The database is only read once per run.

Virtualize

Ontop

The graph never exists as triples. A SPARQL query is rewritten into SQL, at query time, against the live database.

Four axes, and they do not all agree

Freshness, cost, query performance, write access

Freshness: as of last run
Cost: query is cheap, triple
  store storage is not free
Query perf: fast, indexed
  like any triple store
Write access: read-only copy,
  source can still be edited
Freshness: always current
Cost: no duplicate storage,
  DB carries the query load
Query perf: bounded by SQL
  rewriting and the DB itself
Write access: same source,
  no separate copy to drift
Run one, not described

Morph-KGC 2.10.0, the mapping from two slides ago, real Postgres

ul:po88 a ul:PurchaseOrder ;
  ul:hasCarrier ul:dhl ;
  ul:dispatchDate "2026-03-10"^^xsd:date ;
  ul:deliveryDate "2026-03-14"^^xsd:date .

ul:po99 a ul:PurchaseOrder ;
  ul:dispatchDate "2026-03-20"^^xsd:date ;
  ul:deliveryDate "2026-03-18"^^xsd:date .
  # no ul:hasCarrier at all
  • po88 materializes exactly as expected, three properties, one carrier.
  • po99's carrier column does not match any row in carriers: the join fails, and produces no triple, not an error.
  • The next slide is about exactly why that second line is a real problem.
The real finding, this session

A broken foreign key does not fail. It goes quiet.

Nothing in the materialize step complained. Morph-KGC ran cleanly, exit code zero, and simply produced two fewer triples than a naive reading of the source data would suggest.

  • A join with no match is not a mapping error. It is defined, silent, and easy to miss.
  • This is exactly the failure mode Session 4's shapes exist to catch, and Part 6 of today runs them against this real output to prove it.
The lesson

A mapping that runs without errors has told you nothing about whether the resulting graph is complete. Only a validator checks that.

The other architecture, same source

Ontop 5.5, an R2RML or native mapping, no materialize step

mappingId  purchase-order-mapping
target     ul:{po_id} a ul:PurchaseOrder ;
  ul:hasCarrier ul:{carrier_code} .
source     SELECT po_id, carrier_code
  FROM purchase_orders
  WHERE carrier_code IS NOT NULL
  • Ontop's own .obda format is more compact than R2RML for the same mapping; it accepts either.
  • A SPARQL query against this mapping never touches a materialized graph. It is compiled, live, into SQL against Postgres.
  • The CLI's real subcommands: query, materialize, endpoint, bootstrap, validate. Today you use query.
Inspecting the rewrite

A SPARQL query in, a SQL query out

SELECT ?po ?carrierName WHERE {
  ?po a ul:PurchaseOrder ;
      ul:hasCarrier ?carrier .
  ?carrier ul:carrierName ?carrierName .
}
What to watch for, live in the lab

Ontop rewrites the property-path join above into a single SQL JOIN between purchase_orders and carriers, with the WHERE carrier_code IS NOT NULL filter from the mapping folded in. You run this exact query with debug logging on, in the lab, and read the real SQL Ontop generated yourself, it is not a fixed answer to memorize.

Part four of six · ~20 minutes

A schema was designed for storage efficiency, not meaning. Translating it takes judgment, not a mechanical rule.

Sequeda and Lassila's patterns, and the ones that look right and are not.

From Sequeda and Lassila

A relational shape has a default graph shape. Not always the right one.

Foreign key

Object property

Already seen: rr:parentTriplesMap plus a join condition. The default, and usually right.

Join table

A relationship

A table with two foreign keys and nothing else becomes a direct property between the two entities it joins.

Denormalized column

A class hierarchy

A status or type column, with a fixed small set of values, often maps better to a subclass than a datatype property.

Pattern two

A pure join table has no identity of its own

<#LegMap> a rr:TriplesMap ;
  rml:logicalSource [ rr:tableName "order_carriers" ] ;
  rr:subjectMap [ rr:template
    "...#{po_id}" ] ;
  rr:predicateObjectMap [
    rr:predicate ul:hasCarrierLeg ;
    rr:objectMap [ rr:parentTriplesMap
      <#CarrierMap> ;
      rr:joinCondition [ ... ] ] ] .
  • The join table itself gets no subject of its own, no type, nothing. Its only job was connecting two other things.
  • If the join table carries its own data, like leg_number above, that column becomes a datatype property on the same statement, or the join table does need its own identity after all.
  • That last case is exactly when a pure relationship pattern stops being enough, judgment, not a rule.
Pattern three

A status column with five values is a class hierarchy in disguise

# one triples map per status value,
# same table, a filtered SQL source
rml:logicalSource [ rr:query
  "SELECT * FROM purchase_orders
   WHERE status = 'cancelled'" ] ;
rr:subjectMap [ rr:template "...{po_id}" ;
  rr:class ul:CancelledOrder ] .
  • Four status values become four subclasses of ul:PurchaseOrder, each with its own filtered logical source, the "logical views" module from Part 2 in real use.
  • Reasoning and SHACL shapes can now target ul:CancelledOrder directly, instead of every query re-checking a string column.
  • Only worth it when the values are stable and few. A column with hundreds of distinct values stays a datatype property.
The trap

A primary key is not always an identity worth an IRI

A surrogate key like an auto-increment id column exists for the database's own indexing needs. Minting ul:{id} from it produces a real, working URI, that is also meaningless outside the database, and breaks the moment the table is reloaded with new IDs.

What to use instead

A natural key the business already relies on, an order number, an ISBN, an account code, or a stable hash of several columns together, if no natural key exists.

Part five of six · ~27 minutes

DataCo and Brunel both have a supplier called something close to "Acme". Are they the same company?

Probably. "Probably" is the whole problem, and it has an honest way to answer it.

The problem, precisely

Two systems, two keys, no shared identifier

DataCo's supplier table and Brunel's supplier table were built independently. Nobody coordinated their primary keys, their name formatting, or even which fields they bothered to fill in.

  • DC-001, "Acme Logistics Ltd" and BR-101, "Acme Logistics" are, in the real world, the same company.
  • No join condition exists that finds this pair. There is no shared key to join on.
The reframe

This is not a mapping problem. It is a classification problem: given a pair of records, decide match or not, with a probability, not a certainty.

The classical model

Compare every field, weigh the evidence, decide

  • For each field, ask two questions: how likely is this level of similarity among true matches (the m probability), and among true non-matches (the u probability)?
  • Combine every field's evidence into one match score. High enough, call it a match; low enough, not; in between, review it.
Why this is not just "similar strings"

Two suppliers sharing a common city is weak evidence, most suppliers in the same city are unrelated. Two suppliers sharing a rare, near-identical name is strong evidence. Fellegi-Sunter weighs fields by how surprising the agreement actually is.

The tractability problem

Comparing every pair does not scale

10,000 DataCo suppliers against 10,000 Brunel suppliers is 100 million pairs. Almost all of them are obviously not matches, and comparing them anyway wastes nearly all the work.

  • Blocking only compares pairs that agree on some cheap key first, same country, same first three letters of a name.
  • Too strict a blocking rule silently drops true matches before comparison ever runs. Too loose, and you are back to comparing almost everything.
Tuning blocking is part of the job

The lab's own blocking rule choice changes the result, tested this session, not a hypothetical: the next two slides show exactly how much.

Not described, run

Splink 4.0.17, DataCo and Brunel suppliers, five real near-duplicates

  • DC-001 "Acme Logistics Ltd" vs BR-101 "Acme Logistics"
  • DC-002 "Brunel Freight Group" vs BR-102 "Brunel Freight Grp"
  • DC-003 "Med Shipping Co" vs BR-103 "Mediterranean Shipping Co"
  • Plus a labeled sample: five true pairs, five true non-pairs, known in advance.
Comparisons used

Jaro-Winkler similarity on name, exact match on city and country, blocked on country to keep the comparison space small, exactly the tradeoff from the last slide.

Real numbers, against the labeled sample

100% recall. 56% precision. Very different problems.

True positives:  5
False positives: 4
False negatives: 0
Precision: 0.556
Recall:    1.000
  • Every real match was found, recall 1.000. Good news, alone.
  • But 4 of the 9 flagged pairs were wrong, different companies that happened to share a country, precision 0.556.
  • A single "accuracy" figure would have buried this entirely. This is exactly why the syllabus, and Splink's own output, report both.
The same model, tuned

Raising the match threshold from 0.5 to 0.8

True positives:  5
False positives: 0
False negatives: 0
Precision: 1.000
Recall:    1.000
Why this worked

The five real matches scored 0.93. The four false positives, same-country strangers, scored 0.57. A wide gap existed, the default threshold of 0.5 just was not tuned to sit inside it. Tuning against a labeled sample is not optional, it is the whole job.

Session 4's shapes were written against hand-placed data. What happens when you point them at a real pipeline's output?

Exactly what they should: they catch the silent gap from Part 3.

The discussion this sets up

A reasoner, a validator, and a mapping engine catch different things

  • OWL asks: is this consistent with everything asserted? It never noticed po99 was missing a carrier at all.
  • SHACL asks: is this graph, as it stands, complete? It caught the gap immediately.
  • Neither one caught the mapping's own silent join failure. Only reading the materialized output, or running the shapes against it, surfaced that.
Carried into the wrap discussion

This is the exact question the 15-minute discussion closes on: which mapping errors did SHACL catch that the reasoner did not, and what does that say about where each belongs in a real pipeline?
