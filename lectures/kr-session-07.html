What the writer must know

The property is ul:carriedBy, not “carry”. The carrier is an IRI built from its code. Neither is in the question.

Large language model A model trained on a huge amount of text. It writes text and code one piece at a time.

Part 2 of 5 · Grounding · about 23 minutes

Grounding: telling the model what the graph holds

Grounding means giving the model the facts it must use. It needs the graph's classes and properties and a few worked examples, not the whole ontology.

Grounding Giving a model the facts it must use, such as the schema and examples, instead of relying on what it remembers.

VoID · what it is for

VoID is a graph's own short description of what it contains

VoID (Vocabulary of Interlinked Datasets) is a W3C standard (2011) for describing a dataset in RDF: where to query it, how big it is, which classes and properties it uses and how often. The ontology says what may be in the graph; VoID says what is in it, with counts. VoID itself does nothing: it is a file, void.ttl, and our code reads it for two jobs. A third is a habit you can add.

Use 1 · Part 2 · in the lab

Tell the model what exists

The code reads the classes, properties and counts from VoID and puts them in the prompt. The prompt could never hold 135,841 triples.

Use 2 · Part 3 · in the lab

VoID · what the file looks like, for Brunel

A summary at class level: how many things, and which property links which classes

Defined on this slide

Class partition: The group of things that have one class, here Plant.

Property partition: How that group uses one property, here makes: how often, and to which class.

<.../brunel/void>
  void:classPartition ul:Plant-partition .
# the group of things of class Plant
ul:Plant-partition void:class ul:Plant ;
  void:entities 19 ;           # 19 plants
  void:propertyPartition ul:Plant-makes .
# how those plants use the property makes
ul:Plant-makes void:property ul:makes ;
  void:triples 2035 ;          # 2,035 links
  # (not 2,036: plant CND9 has no class)
  # the things at the other end are Products
  void:classPartition [ void:class ul:Product ] .

Why plain lines

A model reads text. “ul:Order ul:carriedBy ul:Carrier” says which way the link goes and what is at the other end: all a query writer needs.

The counts help too

ul:LateOrder (192 things) sitting next to ul:Order (9,023) shows that orders come in two kinds.

Why a SHACL word?

SHACL has a word for a stored query, sh:SPARQLExecutable. Public endpoints such as SIB's use it, so other tools can load our examples.

SIB The Swiss Institute of Bioinformatics, whose endpoints and tools (void-generator, sparql-llm) lead in text to SPARQL.

Retrieval: why and how

Choosing the examples closest to the question is retrieval. A real system has hundreds of examples, too many for one prompt, so it keeps the closest. They help most: example 1's query already uses ul:carriedBy, the property this question needs. Here closeness is the number of shared words, ignoring common ones (how, many, did).

Defined on this slide
Prompt
Everything the model is given in one call: rules, schema, examples, question.
The prompt, as text

The prompt has four parts.

# 1. Rules (shortened)
You write one SPARQL 1.1 query for the Brunel graph.
Use only the classes and properties in the schema.
If the schema lacks the kind of fact, reply:
REFUSE: <what is missing>
# 2. Schema (shortened)
ul:Order (9,023 things)
ul:Order ul:carriedBy ul:Carrier
# 3. Examples (shortened) and 4. the question
Question: Which orders did carrier V44_3 carry?
SELECT ?order WHERE { ?order ul:carriedBy ... }
Question: How many orders did carrier V44_3 carry?
What each part does

Rules: what to write, and when to refuse. Schema: the only words allowed. Examples: the style to copy. Question: what to answer now.

Part 3 of 5 · Check, repair, refuse · about 22 minutes

Catching the model's mistakes before the user does

The model will sometimes be wrong. Three steps: check each query before it runs, send the problems back for a second try, and refuse when the graph has no answer. Some mistakes no check can catch.

VoID use 2 · checking a query before it runs · a real run of check.py

Two tests: is it SPARQL, and is every ul: property listed in void.ttl?

}
broken.sparql: 1 problem

Access control on a graph, and what the model is allowed to see

Ask as the user

The layer queries with the asker's rights, never an administrator's. Fuseki can limit each user to named datasets and graphs.

Send the schema, not the data

The model gets VoID and examples. The rows stay in your stack. A free tier's inputs may be used to improve the provider's products.

Keep keys out of code

The key lives in .env, which is never committed. A key in a script or a slide is a leaked key.

Open problems · about 22 minutes

Six questions the field has not answered yet

In this course we checked every answer after it was produced. These six questions ask what it would take to not need that. Each team picks one for its report.

Open problem 1 of 6

Ontology learning from text

Can a model write the ontology Session 3 wrote by hand, from documents?

Why it is open

Models now suggest classes and relations well enough to help, but not well enough to trust: someone must still decide what the words mean.

Read

Asim and others, Database, 2018 (a survey) · Babaei Giglou, D'Souza and Auer, “LLMs4OL”, ISWC 2023

Ontology learning Building an ontology, or parts of it, automatically from text or data.

Open problem 2 of 6

Constraints by construction

Can a learned model obey a rule because of how it is built, not because we check its output?

Why it is open

Sessions 4 and 7 check afterwards: SHACL, the query check. Building the rule into training is possible for simple logic, hard for real shapes.

Read

Xu and others, “A semantic loss function”, ICML 2018 · Giunchiglia and Lukasiewicz, JAIR, 2021

Open problem 3 of 6

Do models reason over ontologies?

When a model scores well on a benchmark, did it reason, or remember?

Why it is open

A model may have seen the benchmark in training. Today's score, like ours, shows answers, not how they were reached.

Read

He and others, “Language model analysis for ontology subsumption inference”, Findings of ACL 2023 · Sainz and others, Findings of EMNLP 2023

Open problem 4 of 6

Time and space

How do you ask when something was true, or how near two things are?

Why it is open

This course left them out: Brunel has one order date. Facts that change over time, and places, need more than plain triples.

Read

Gutierrez, Hurtado and Vaisman, IEEE TKDE, 2007 · OGC GeoSPARQL 1.1, 2024

Open problem 5 of 6

Reproducible results

Do reported gains in knowledge graph completion still hold in a fair comparison?

Why it is open

Several did not: tuned old models matched new ones. Session 6's baseline was this lesson on our own data.

Read

Kadlec, Bajgar and Kleindienst, 2017 · Ruffinelli, Broscheit and Gemulla, ICLR 2020 · Sun and others, ACL 2020

Open problem 6 of 6

Standards in motion

What do you build on when the standard is still changing?

Why it is open

SHACL 1.2 Core is a W3C Working Draft (18 September 2026). The RML Working Group is not yet chartered; its charter was being refined from June 2026.

Read

W3C, SHACL 1.2 Core, Working Draft · W3C strategy issue 443, the RML Working Group charter

def unknown_properties(query, classes, props):
    known = {p.split("#")[1] for p in props}
    used = {t for t in ul_terms(query)
            if t[0].islower()}
