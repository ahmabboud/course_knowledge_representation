Part 1 of 5 · about 30 minutes

A table stores rows. A graph stores statements. What is the difference, and why pay for it?

One real Brunel order, taken apart into statements, one step at a time.

The problem

Session 1's question follows links: plant, port, carrier, customer. Tables hide links in columns.

The smallest unit

Every fact in RDF has the same three parts. One fact is one triple.

<https://ul.edu.lb/kr/id/order/brunel/1447296446.7>
  <https://ul.edu.lb/kr/scm#fromPlant>
  <https://ul.edu.lb/kr/id/plant/brunel/PLANT16> .
Defined on this slide

RDF: Resource Description Framework: a graph written as a list of three part statements.

Triple: one statement: subject, predicate, object. One edge of the graph.

Names for things

Every thing gets a globally unique name, an IRI, built from parts you choose.

@prefix ul:    <https://ul.edu.lb/kr/scm#> .
@prefix order: <https://ul.edu.lb/kr/id/order/brunel/> .

order:1447296446.7  ul:fromPlant  plant:PLANT16 .
Defined on this slide

IRI: Internationalised Resource Identifier: a globally unique name, written like a web address.

Namespace: the shared first part of a group of IRIs.

Prefix: a short nickname for a namespace, such as ul:.

Plain values

Not everything is a thing. A weight or a date is a literal, and it has a datatype.

Defined on this slide

Literal: a plain value in a triple: a number, a date, a piece of text.

Datatype: the kind of a literal, such as integer or date.

Why the ID is text

Read as a number, 1447296446.7 is a decimal to be rounded and summed. It is a name. Text keeps it exact.

Worked example

The first row of OrderList becomes 13 triples. This is what convert_to_rdf.py does 9,215 times.

Joining by naming

Two tables that share a code share a node. The graph is already joined.

A freight rate band has no ID in the source. It is only its carrier, lane and weight range.

Blank node: a node with no global name, for something that matters only through its links.

Defined on this slide

Named graph: a set of triples with its own IRI, used to track where they came from.

Why it matters by Session 5

When two sources disagree, you must know which one said what. The graph name is that record.

Serializations

The same triples can be written three ways. Pick by who reads them.

order:1447296446.7 a ul:Order ;
  ul:fromPlant plant:PLANT16 ;
  ul:weight 14.3 ;
  ul:serviceLevel "CRF" .

Authoring and reading.

<.../order/brunel/1447296446.7>
  <...scm#weight>
  "14.3"^^<...XMLSchema#decimal> .

One triple per line: split, stream, load.

{ "@id": ".../order/brunel/1447296446.7",
  "@type": "ul:Order",
  "ul:serviceLevel": "CRF" }

JSON that is also RDF.

Defined on this slide

Turtle: a compact, readable text format for triples.

N-Triples: one full triple per line, simple to process in bulk.

JSON-LD: triples written as JSON, used by web APIs.

Part 2 of 5 · about 8 minutes

Your IRI scheme is a contract with every future data source. Which scheme survives?

Three real ways to name a Brunel order. Two of them break.

The decision you cannot quietly undo

Three ways to name the first Brunel order. Watch what breaks, and when.

SchemeThe IRIIt breaks when
Row number.../order/1The file is sorted differently, or a row is deleted. Every name shifts.
Key only.../order/1447296446.7A second system also has an order 1447296446.7. Two different orders, one name.
Kind, source, key.../order/brunel/1447296446.7Survives both. A second source gets its own space.
The third is what common/iri.py mints today.
The trap

One IRI per real thing, not per row, and not one per string that looks alike. Two systems' orders get two IRIs; deciding they are the same is a Session 5 decision, with evidence.

Three rules

Name things so the next source cannot lie to you by accident.

  1. Say which system minted it. You will have two sources by Session 5.
  2. Never put anything that changes into an IRI: names, status, country. Keys do not change; names do.
  3. Words and things live apart. ul: (ends in #) for classes and properties. .../kr/id/ (ends in /) for things, so each can have its own web page later.
VOCAB = "https://ul.edu.lb/kr/scm#"
DATA  = "https://ul.edu.lb/kr/id/"

def order_iri(source, key):
    return f"{DATA}order/{source}/{key}"
Part 3 of 5 · about 12 minutes

The graph has names. Can it say anything about what an order is?

A small schema, written as triples too, and the first surprise: it concludes instead of checking.

The first schema

RDFS adds a few words for describing the data, written as triples like the data itself.

Defined on this slide

rdf:type: the predicate that says what class a thing belongs to (written a).

RDFS: RDF Schema: the first vocabulary for classes and properties: subclass, domain, range, label.

The most important difference in the course

RDFS never rejects data. It concludes new facts from it.

Real run: rdfs_entailment_demo.py, rdflib with owlrl, 2.6 seconds.

Defined on this slide

Entailment: a fact that follows from stated facts and rules, even though nobody wrote it down.

Constraint: a rule data must obey; breaking it is reported as an error. That is Session 4.

Check question

The schema says the domain of ul:carriedBy is ul:Order. A port is given a carrier by mistake. What does an RDFS reasoner do?

The habit this trains

Inference adds facts; validation refuses data. Never use one for the other's job.

Part 4 of 5 · about 34 minutes

How do you ask a graph a question?

Draw the shape of the answer, with holes in it. Every result on these slides is a real run on our 135,841 triples.

The core idea

A SPARQL query is a picture of the answer, with holes for what you want to know.

PREFIX ul: <https://ul.edu.lb/kr/scm#>
SELECT (COUNT(*) AS ?n) WHERE {
  ?order ul:carriedBy carrier:V44_3 .
}
Defined on this slide

SPARQL: the query language for RDF graphs.

Triple pattern: a triple with some parts replaced by variables.

Variable: a placeholder, written ?name, filled by every match.

Joins without JOIN

Two patterns that share a variable must match the same thing. That is the whole join mechanism.

?order ul:carriedBy ?carrier ;
       ul:lateDays  ?late .      # ; repeats the subject ?order
Missing parts and conditions

OPTIONAL keeps a row even when part of the pattern has no match. FILTER removes rows.

SELECT ?carrier (COUNT(?band) AS ?bands) WHERE {
  ?carrier a ul:Carrier .
  OPTIONAL { ?band ul:bandCarrier ?carrier }
} GROUP BY ?carrier ORDER BY ?bands
?carrier?bands
V44_30
V444_039
V444_1292
Real result, Fuseki, 12.5 ms.
Without OPTIONAL

V44_3 would vanish from the result, and the finding with it. OPTIONAL is how a missing link stays visible.

Numbers from the graph

GROUP BY and COUNT turn matches into a table of totals.

SELECT ?carrier (COUNT(?order) AS ?orders)
       (SUM(IF(?late > 0, 1, 0)) AS ?lateOrders)
WHERE { ?order ul:carriedBy ?carrier ;
              ul:lateDays ?late . }
GROUP BY ?carrier ORDER BY DESC(?orders)
CarrierOrdersLate
V444_06,264183
V444_12,0979
V44_38540
Real result, Fuseki, 47 ms.
Defined on this slide

Aggregation: combining many matches into one number (a count, a sum, an average), grouped by something.

Federation, in one line

A query can also reach another endpoint with SERVICE <url> { ... }. We do not run it in the lab; know that it exists.

One character, many hops

A property path follows links in sequence, or any number of times.

Defined on this slide

Property path: a shortcut to follow a relationship in sequence (/), one or more times (+), or zero or more times (*).

Where SPARQL is better, and where it is not

Any depth is one character in SPARQL. In SQL it is a recursive query.

SELECT (COUNT(?o) AS ?n) WHERE {
  ?o a/rdfs:subClassOf* ul:Order .
}
WITH RECURSIVE sub(cls) AS (
  SELECT 'Order'
  UNION
  SELECT c.child FROM class_parent c
  JOIN sub ON c.parent = sub.cls )
SELECT COUNT(*) FROM orders o
JOIN sub ON o.type = sub.cls;
SPARQL wins

Paths of unknown length, data from many sources with one set of names, and a schema you can query like data.

SQL wins

Fixed, well known tables, heavy arithmetic, and decades of tuning. For a monthly sales total, use SQL.

Neo4j is the most used graph database. Why does this course use RDF?

The same orders, loaded into both. The difference shows up in one question.

The property graph

In Neo4j, nodes have labels and key value properties, and edges have types.

MATCH (o:Order {id: '1447296446.7'})
      -[r]->(n)
RETURN o, r, n
Defined on this slide

Property graph: nodes and edges that carry labels and properties, as in Neo4j.

Cypher: the query language of Neo4j: patterns drawn with brackets and arrows.

One question shows the difference

How many orders are there, counting late orders as orders?

?o a/rdfs:subClassOf* ul:Order

Answer 9,215. The fact that a late order is an order lives in the graph, once, for every query.

MATCH (o:Order) ...                  // 9,023
MATCH (o) WHERE o:Order OR o:LateOrder  // 9,215

A label is a string. Neo4j has no subclass, so every query must list the kinds itself.

RDF gives youThe property graph gives you
Global names: graphs from two companies merge without a meetingProperties on edges without extra ceremony
A schema you can query and reason over (RDFS, OWL, SHACL)A friendlier query language, and wide industry use
