Part one of three · 20 minutes

What if adding a new kind of fact needed no migration at all?

A relational schema is agreed on once and changed carefully. RDF has exactly one shape, forever, so nothing has to be agreed on in advance.

The whole model

Subject, predicate, object. There is no second construct.

  • Subjects and predicates are .
  • Objects are IRIs or literals.
  • That is the entire data model. There is no table, no column, no schema to alter first.
ship-4471
carrier-dhl

Subject, predicate, object: one labelled edge, drawn exactly as it is stored.

Two consequences of having one construct

The schema lives in the same graph, and is queried the same way.

ul:ship-4471 a           ul:Shipment ;
    ul:daysLate    6 ;
    ul:departedFrom ul:plant-P114 .

# and the vocabulary itself:
ul:LateShipment rdfs:subClassOf ul:Shipment .

The semicolon repeats the subject. The last line is schema, not data, and it is stored identically.

  • A literal carries a datatype: "6"^^xsd:integer. The ^^ is Turtle for "typed as".
  • Because the vocabulary is triples, you can query it. That is what makes OWL and SHACL possible at all.
This is the answer to the EAV objection

Global names and a standard query language. An EAV table federates with nothing; a graph merges with a partner's graph you have never seen.

The decision you cannot quietly undo

Your IRI scheme is a contract with every future data source.

# Breaks when ERP is not the only source
ul:supplier-V8841

# Breaks when the name changes
ul:supplier-Nordwind-Components-GmbH

# Survives both
ul:supplier/erp/V8841
What breaks, and when

The first does not collide when the WMS extract arrives, which is worse than colliding: you cannot tell which V8841 you are holding.

Three rules and one trap

Name things so the next source cannot lie to you by accident.

  • Say which system minted it. You will have two sources by Session 5.
  • Never encode anything that changes: names, status, country.
  • Opaque keys are fine. Readable keys are kinder to debug.
Trap

One IRI per real thing, not per row. The same supplier in two systems is two IRIs and a Session 5 decision, not a silent merge now.

Check question

You will load a second supplier source in Session 5. Which scheme survives it?

The habit

Separate what a name identifies from what it describes.

Part two of three · 26 minutes

What can this graph answer that SQL genuinely struggles with?

Most of SPARQL is familiar. One part of it is the reason the graph exists at all.

Vocabulary, quickly

Four ways to ask, and only one returns a table.

SELECT
Rows and columns. What you will use all afternoon.
ASK
True or false. Cheap, and the right shape for a constraint check.
CONSTRUCT
Returns a graph, so it composes with other queries.
DESCRIBE
Whatever the endpoint thinks is relevant. Rarely what you want.

It takes a graph and returns a graph. In Session 5 you use it to reshape a mapped graph without touching the mapping, and in Session 7 the agent uses it to build a small answer graph it can cite from.

The mental model

You draw the shape you want. The engine finds every match.

SELECT ?carrier (COUNT(?s) AS ?n)
WHERE {
  ?s ul:handledBy ?carrier ;
     ul:daysLate  ?d .
  FILTER(?d > 0)
}
GROUP BY ?carrier
  • Those two lines inside WHERE are a shape with holes in it. Every match fills the holes.
  • OPTIONAL is the left join. FILTER is the WHERE clause.
The one sentence

In SQL you say how to join. In SPARQL you say what the answer looks like.

The reason the graph exists

"Any depth of sub-assembly" is one character.

# Every part, at any depth
?good ul:hasComponent+ ?part .

This is the Session 1 sanction question: which finished goods contain a part from that plant.

+
one or more hops
*
zero or more
/ and |
sequence, alternative
^
follow the edge backwards
The same question in SQL

Nine lines, a recursive CTE, and a join you have to get right.

WITH RECURSIVE bom(good, part) AS (
  SELECT good, part FROM component
  UNION ALL
  SELECT b.good, c.part
  FROM bom b JOIN component c
    ON c.good = b.part )
SELECT * FROM bom;
Honest limit, say this out loud

The CTE works and is not exotic. The argument is expressiveness, not capability. And paths are expensive: on a large graph an unbounded + is where your query goes to die.

Part three of three · 11 minutes

Four companies must merge their graphs with no shared database. Which model survives that?

You will meet property graphs in industry more than RDF. This part is about the one thing only one of them can do.

Same fact, two encodings

One shipment, one carrier, written both ways.

A modelling choice, not a vendor preference

Only one of them can carry a schema you can reason over.

RDF gives you
  • Global names, so graphs merge without a meeting.
  • A queryable vocabulary, which is what makes OWL and SHACL possible.
The property graph gives you
  • Edge properties without ceremony, and a friendlier language.
  • But the label is a string, and a string cannot be reasoned over.

Inside the lab · worked method

Put the conversion in the order you will actually work in.

  • Emit one triple per column that carries meaning
  • Decide what the rows are about, and which column identifies it
  • Query for a fact you know is true, to prove the load worked
  • Design the IRI for that thing, including its source system
  • Turn foreign keys into IRIs, not string literals
Step 4 is where most marks are lost

A foreign key left as a literal makes a graph you cannot traverse. ul:order-101 ul:fromPlant "PL2" is a dead end; ul:plant-PL2 is an edge.

Discussion · 20 minutes

Compare IRI schemes in pairs. Find the one that breaks first.

  • Show your partner your scheme and the three lines defending it.
  • Try to break it: a second source, a renamed supplier, a merged company.
  • Bring back the convention you would both adopt.
Outcome

The cohort agrees one IRI convention before leaving. From Session 3 everyone models against it, and in Session 5 it is what makes two sources reconcilable.

Wrap

A graph is not a better table. It is a data model where the schema is data, which is the only reason a machine can reason about meaning at all.
