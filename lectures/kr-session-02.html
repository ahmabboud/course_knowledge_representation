Part one of three · 20 minutes

One data structure, all the way down

RDF has exactly one shape. Everything else today is a consequence of that.

The whole model

Subject, predicate, object. There is no second construct.

  • Subjects and predicates are . Objects are IRIs or literals.
  • A literal carries a datatype: "6"^^xsd:integer.
  • The schema is triples too, in the same graph, queried the same way.
What this buys

No table to alter. Adding a fact about a supplier is adding a row, never a migration.

@prefix ul: <https://ul.edu.lb/kr/scm#> .

ul:ship-4471 a              ul:Shipment ;
    ul:handledBy   ul:carrier-dhl ;
    ul:daysLate    6 ;
    ul:departedFrom ul:plant-P114 .

Four triples. The semicolon repeats the subject.

The decision you cannot quietly undo

Your IRI scheme is a contract with every future data source.

# Breaks when ERP is not the only source
ul:supplier-V8841

# Breaks when the name changes
ul:supplier-Nordwind-Components-GmbH

# Survives both
ul:supplier/erp/V8841
  • Say which system minted the identifier. You will have two sources by Session 5.
  • Never encode anything that changes: names, status, country.
  • Opaque keys are fine. Readable keys are kinder to debug.
Trap

One IRI per real thing, not per row. The same supplier in two systems is two IRIs and a Session 5 decision, not a silent merge now.

Check question

You will load a second supplier source in Session 5. Which scheme survives it?

The habit

Name things so that the next source cannot lie to you by accident.

Part two of three · 25 minutes

SPARQL, and the question SQL is bad at

Most of SPARQL is familiar. One part of it is the reason the graph exists.

The mental model

You draw the shape you want. The engine finds every match.

SELECT ?carrier (COUNT(?s) AS ?n)
WHERE {
  ?s ul:handledBy ?carrier ;
     ul:daysLate  ?d .
  FILTER(?d > 0)
}
GROUP BY ?carrier

A basic graph pattern is a set of triples with variables in it.

  • SELECT for tables, ASK for yes or no, CONSTRUCT for a new graph, DESCRIBE for whatever the endpoint thinks is relevant.
  • OPTIONAL is the left join. FILTER is the WHERE clause.

It takes a graph and returns a graph, so it composes. In Session 5 you will use it to reshape a mapped graph without touching the mapping, and in Session 7 the agent uses it to build a small answer graph it can cite from.

The reason the graph exists

"Any depth of sub-assembly" is one character.

# Every part, at any depth
?good ul:hasComponent+ ?part .
WITH RECURSIVE bom(good, part) AS (
  SELECT good, part FROM component
  UNION ALL
  SELECT b.good, c.part
  FROM bom b JOIN component c
    ON c.good = b.part )
SELECT * FROM bom;
  • + one or more, * zero or more, / sequence, | alternative, ^ reverse.
  • This is the Session 1 sanction question: which finished goods contain a part from that plant.
Honest limit

Paths are expensive and hard to predict. On a large graph an unbounded + is where your query goes to die.

Part three of three · 12 minutes

The other graph model

You will meet property graphs in industry more often than RDF. Know exactly what each one gives up.

A modelling choice, not a vendor preference

One of these can carry a schema you can reason over.

RDF 
ul:ship-4471 ul:handledBy ul:carrier-dhl .
ul:LateShipment rdfs:subClassOf ul:Shipment .
  • Global names, so graphs merge without a meeting.
  • The vocabulary is queryable, which is what makes OWL and SHACL possible.
Property graph 
(s:Shipment {id:'4471'})
  -[:HANDLED_BY {cost:812}]->
(c:Carrier {name:'DHL'})
  • Properties on edges without ceremony, friendlier language.
  • The label is a string. Nothing defines it, so nothing can reason over it.

Deliverable · end of session

If JDK 21 fails you

Fall back to Oxigraph through pyoxigraph. Same queries, no Java, and it is the path you want above a million triples anyway.

Inside the lab · worked method

Put the conversion in the order you will actually work in.

  • Emit one triple per column that carries meaning
  • Decide what the rows are about, and which column identifies it
  • Query for a fact you know is true, to prove the load worked
  • Design the IRI for that thing, including its source system
  • Turn foreign keys into IRIs, not string literals
Step 4 is where most marks are lost

A foreign key left as a literal makes a graph you cannot traverse. ul:order-101 ul:fromPlant "PL2" is a dead end; ul:plant-PL2 is an edge.

A load that silently produced zero triples looks identical to one that worked, until you query it. Pick a fact you can verify by eye in the source table, ask for it, and only then trust the rest.

Discussion · 20 minutes

Compare IRI schemes in pairs. Find the one that breaks first.

  • Show your partner your scheme and the three lines defending it.
  • Try to break it: a second source, a renamed supplier, a merged company.
  • Bring back the convention you would both adopt.
Outcome

The cohort agrees one IRI convention before leaving. From Session 3 everyone models against it, and in Session 5 it is what makes two sources reconcilable.

Wrap

One sentence to leave with.

A graph is not a better table. It is a data model where the schema is data, which is the only reason a machine can reason about meaning at all.
