Part one of six · ~14 minutes

You could flatten every table into one row per order and hand it to a gradient-boosted tree. Why build a graph model at all?

Sometimes you should not. That answer is today's first honest lesson, not a footnote.

Set the terms honestly

A gradient-boosted tree on the flattened join is not a straw man

Denormalize the graph back into one row per order: the order's own fields, plus its supplier's, product's, plant's, port's and carrier's static attributes copied onto that row. Feed it to XGBoost.

  • No message passing, no embeddings, minutes to train, easy to explain to a non-technical stakeholder.
  • It only sees what is on that one row. A pattern that lives in the graph's structure, two suppliers sharing a port neither one's own columns record, is invisible to it.
The honest question this session answers

Not "which is better". When does the graph's structure carry a signal the flattened row cannot, and when is the flattened row already enough? Today's own lab produces a real, un-cherry-picked answer for one task.

The real advantage, stated precisely

Structure helps when the label depends on a neighbor's neighbor

A flattened row can only encode what one entity's own columns record. A graph model can propagate information across hops: a product's risk depends on its plant, which depends on which port serves it, which depends on which carrier operates there.

This is also exactly where the ontology earns its keep: the class hierarchy and property definitions from Sessions 3 and 4 are what determine which node and edge types even exist to learn over. A sloppier ontology gives a sloppier graph, which gives a worse model, before a single weight is trained.

Held for later, with real numbers

Part 5 closes the loop: the same late-delivery task, a real gradient-boosted baseline, and two real graph models, run for real on the same split. The honest scorecard is worth waiting for.

Check question

A team's late-delivery signal turns out to depend entirely on the order's own declared SLA and the carrier's own historical late rate, both already columns on the flattened row. What is the strongest reason to still reach for a graph model here?

Part two of six · ~26 minutes

Will supplier ul:acme ever supply product ul:widget-9? That edge does not exist yet. Score it anyway.

Link prediction, and the evaluation mistake that is easy to make without noticing.

Four scoring functions, one shared idea

Embed entities and relations, score a triple by geometry

Every entity and every relation gets a learned vector. A candidate triple (head, relation, tail) is scored by a fixed geometric rule on those vectors, no message passing yet, just embeddings and arithmetic.

TransE
head + relation ≈ tail. Translation in vector space, today's lab.
DistMult
A bilinear product, symmetric by construction, cannot model direction.
ComplEx
Complex-valued embeddings, fixes DistMult's symmetry problem.
RotatE
Relations as rotations in complex space, captures composition patterns the others miss.
The task, precisely

Link prediction: given (supplier, supplies, ?), rank every candidate product by score. A good model ranks real supplier/product pairs near the top and everything else near the bottom.

Training signal

A model that scores everything highly has learned nothing

The graph only records true triples. Without counter-examples, pushing every real triple's score up is free, embeddings collapse to a trivial solution that scores everything the same.

Negative sampling fixes this: corrupt a real triple by swapping its head or its tail for a random entity, and train the model to score the real triple above its corrupted version.

How far is too far

More layers is not always a better model

Oversmoothing
Stack enough layers and every node's embedding converges toward the same average, distinct nodes become indistinguishable, exactly the opposite of the goal.
Transductive
The model is trained on a fixed graph and only ever asked about nodes already in it. Most academic GNN benchmarks are this.
Inductive
The model must generalize to nodes or edges that did not exist at training time. A new order next week. Closer to the real deployment story.
Held for Part 5, with a real number

Today's own leakage demo needed to switch from transductive to inductive evaluation before a real distribution shift in the data actually showed up as a model failure. That switch mattered more than the split itself.

Part four of six · ~25 minutes

Every real enterprise graph has typed nodes and typed edges. Plain message passing was not built for that.

Two ways to teach it, run and compared for real, this session.

Not described, printed

Six node types, nine relation types, one real object

HeteroData(
  supplier={ x=[10, 4] },
  product={ x=[12, 6] },
  plant={ x=[4, 4] },
  port={ x=[4, 5] },
  carrier={ x=[3, 2] },
  order={ x=[360, 3], y=[360] },
  (order, ordered_from, supplier)=...
  (order, shipped_via, carrier)=...
  -- 9 relation types total --
)

Exactly the six node types the syllabus names: supplier, product, order, plant, port, carrier. 360 orders, 170 late, 47.2 percent, the label this whole session predicts.

Every node and edge type traces back to a class or property Session 3's ontology defined. This object is the ontology, instantiated as tensors.

A real bug, not a hypothetical one

The one-line version, and the error it actually threw

def to_hetero(module, metadata,
    aggr='sum', input_map=None, debug=False)
# metadata = HeteroData.metadata():
#   (node_types, edge_types)

Wrap an ordinary GraphSAGE module, hand it the graph's own metadata, and it rewrites the module per node and edge type automatically, via torch.fx tracing.

What actually happened, first attempt

ValueError: Cannot generate a graph node 'relu' for type 'order' since it does not exist. Every edge was built order→neighbor, so order was never a message destination, its embedding was never produced. Fix: T.ToUndirected() before to_hetero().

The second way

One relation-specific weight matrix per edge type

RGCNConv.__init__(self, in_channels, out_channels,
  num_relations, num_bases=None,
  num_blocks=None, aggr='mean', ...)

RGCNConv.forward(self, x,
  edge_index, edge_type=None)

Not a HeteroData object, a single homogeneous graph plus an integer edge_type per edge. Today's 9 relation types, with reverses added by hand for a fair comparison, became num_relations=18.

The parameter explosion, named for real

One full weight matrix per relation id scales badly. num_bases and num_blocks are real, verified constructor arguments that exist specifically to regularize this away, basis- and block-diagonal decomposition.

Part five of six · ~26 minutes

A random split gave this session's model a great number. A random split is also the wrong question to ask a supply chain graph.

The part most published work gets wrong, reproduced honestly, with real numbers.

The mechanism

Randomness hides a distribution shift, it does not remove one

A supply chain changes over time: a port gets congested, a carrier's contract changes, a plant opens. A model trained on data from every period and tested on a random sample from every period has effectively seen the future during training.

  • Split edges when the question is about relationships forming, not about which node exists.
  • Split temporally whenever time is a real dimension in the domain, which for a supply chain, it always is.
Today's own reproduction

A real port-congestion regime change was injected into this session's synthetic data specifically to make this failure mode visible, honestly, rather than asserted from a textbook.

What was actually injected

Port of Hamburg, a genuine congestion event, 2026-01-01

Port of Hamburg, BEFORE 2026-01-01:
  late rate 41.7%  (n=36)
Port of Hamburg, AFTER  2026-01-01:
  late rate 100.0%  (n=42)
All other ports, overall:
  late rate 40.1%  (n=282)
Deliberately not given to the model directly

No feature encodes the regime change itself. The only way a model can learn about it is by having actually seen orders from after the cutoff during training, exactly the thing a temporal split withholds.

The honest caveat, run for real

The exact gap is noisy. The qualitative story is not.

seed=0  gap=+0.1574   seed=1  gap=+0.0370
seed=2  gap=+0.1019   seed=3  gap=+0.1204
seed=4  gap=-0.0093
Temporal acc <= its baseline: 5/5 seeds

One seed even shows a small negative gap, report that honestly rather than hiding it. The magnitude varies run to run on a small graph.

What stays true in all five

The temporally-split model never once beat its own trivial majority-class baseline. The randomly-split model usually did. That asymmetry, not any single accuracy figure, is the defensible finding.

The part a textbook skips

A real regime change alone was not enough

The first attempt: a plain random-vs-temporal relabeling of a static graph, trained and evaluated transductively (the whole graph visible throughout). It showed no gap at all.

A transductive model's message passing sees every node's features regardless of which split assigned a label, so relabeling alone withholds nothing structural.

What actually made it work

Switch to inductive evaluation: the train-time graph contains only train-period orders and edges, test orders are added only at evaluation time. Only then does withholding "the future" have any structural effect at all.

Show of hands, no scoring, 45 seconds

Both graph models here lose to XGBoost on F1, the metric that matters most for a rare "late" class. What should a Milestone 2 report do with that?

Tempting, and wrong

Keep tuning the graph model until it wins, then report that. This is exactly how a random-split-shaped mistake happens again, optimizing against the metric you want rather than reporting the one you got.

The right call

Report it as-is, with an honest explanation of why. A graph model losing to a strong tabular baseline, explained honestly, is a legitimate and gradeable result per the syllabus, not a failure to hide.
